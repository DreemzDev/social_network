# storage — единый сервис хранения файлов

## 1. Назначение модуля

`storage` — единственная точка входа для работы с файлами, у которых есть хотя бы
одно из свойств: нетривиальные права доступа, ограниченный срок жизни,
разделяемость между модулями. Такие файлы не хранятся модулями самостоятельно —
ни один потребитель не объявляет собственный `FileField` для них и не пишет
напрямую в `MEDIA_ROOT`.

Модуль отвечает за:

- физическое хранение содержимого (одно содержимое — одна копия на диске);
- метаданные (имя, размер, MIME-тип, контрольная сумма, автор, дата, категория);
- жизненный цикл содержимого: `ACTIVE → ORPHAN → физическое удаление`;
- API (`StorageService`), через который остальные приложения загружают,
  отвязывают и отдают файлы;
- ограничение размера и учёт занятого места;
- аудит операций над файлами.

Модуль **не отвечает** за:

- права доступа «кто может увидеть этот файл» — это бизнес-логика
  модуля-потребителя (раздел 8);
- корзину и восстановление удалённого — это тоже уровень потребителя
  (раздел 6);
- смысл файла (документ, вложение чата, приказ) — storage знает лишь
  категорию для расчёта срока хранения, но не бизнес-семантику.

### 1.1. Что использует storage, а что нет

Критерий: файл идёт в storage, если у него есть **хотя бы одно** из трёх —
нетривиальные права доступа, ограниченный срок жизни, разделяемость между
модулями. Если нет ни одного — обычный `FileField`/`ImageField` проще и
честнее, а перевод такого файла в storage добавит слой абстракции, ничего не
дав взамен.

**Остаются на обычных полях (не трогаем):**

| Модель | Поле | Почему не в storage |
|---|---|---|
| `profiles.User` | `avatar` | одно изображение на пользователя, видят все, живёт вместе с пользователем, дедуплицировать нечего |
| `posts.PostImage` | `image` | публичны (видны всем, кто видит пост), не переиспользуются, нужны превью/сжатие — этого в storage нет |
| `gallery.GalleryImage` | `image` | галерея общедоступна, приватных альбомов нет и не планируется |

**Переводятся в storage:**

| Модель | Поле | Почему в storage |
|---|---|---|
| `posts.PostFile` | `file` | документы (приказы, бланки, инструкции), которые будут дублироваться с информационным каталогом и пересылаться в чате — дедупликация даёт реальную экономию |
| `phonebook.Phonebook` | `book` | по смыслу тот же каталог документов, логично держать в одной системе |

Обратите внимание: у постов **изображения и файлы разведены по разным
моделям** (`PostImage` / `PostFile`) — это позволяет перевести документы в
storage, не трогая картинки.

**Но одно свойство storage нужно и им: файл не должен переживать свою
запись.** Django не удаляет файл при удалении модели и не удалял никогда —
это убрали в 1.3, потому что откат транзакции возвращает строку, а файл
вернуть уже неоткуда. В результате картинки накапливались молча: на момент,
когда это заметили, в `media/` лежало 58 файлов (~43 МБ) при **нуле**
ссылающихся записей — 17 в галерее, 27 у постов, 14 аватаров. Аватары
показательны отдельно: их не удаляли, их меняли, и каждая смена оставляла
прежний файл, потому что `FileSystemStorage` даёт новому имя с суффиксом, а
не перезаписывает старое.

Отсюда `storage/mediafiles.py` — уборка за обычными `ImageField`, а не
перевод их в storage:

- `register_file_cleanup(model, *fields)` вызывается из `AppConfig.ready()`
  того приложения, которому поле принадлежит: storage не обязан знать своих
  потребителей, а список полей лежит рядом с моделью;
- удаление откладывается через `transaction.on_commit()` — по той же
  причине, по которой Django отказалась удалять файлы сама;
- при **замене** значения удаляется прежний файл, но `update_fields`
  проверяется обязательно: `UserActivityMiddleware` зовёт
  `save(update_fields=['last_activity'])` на каждый запрос, и без этой
  проверки каждый переход по порталу стоил бы лишнего SELECT;
- регистрация **явная, по полям**, а не обход всех `FileField` проекта:
  `FileBlob.file` такому механизму противопоказан — на один файл ссылается
  несколько `FileObject`, и удаление по исчезновению одной записи снесло бы
  файл из-под остальных. Закреплено тестом
  (`test_media_cleanup.RegistryTest.test_blob_file_is_not_registered`);
- накопившееся убирает команда `media_verify [--delete-untracked]` — тот же
  принцип, что у `storage_verify`, но сверяет только каталоги
  зарегистрированных полей. Каталог `storage/` она не видит принципиально:
  файл без `FileObject` там — законный `ORPHAN`, ждущий своего срока
  (раздел 7), а не мусор.

**Второе, что нужно картинкам и противопоказано storage: сжатие.**
`storage/images.py` уменьшает загруженный снимок до `IMAGE_MAX_SIDE`,
пересжимает и собирает миниатюру (`IMAGE_THUMBNAIL_SIDE`) для сетки.
Документам такое нельзя даже теоретически: файл в storage обязан доезжать
до получателя байт в байт, его checksum — основа дедупликации. Отсюда и
раздельные модули: `StorageService` содержимое не трогает вообще,
`images.py` работает только с полями, которые ему передали явно.

Что здесь важно помнить:

- «без потери качества» в строгом смысле (lossless-оптимизация PNG) даёт
  проценты. Выигрыш дают уменьшение стороны, пересжатие и **миниатюра** —
  последняя больше остальных вместе: в сетке нужен снимок 480 px, а не
  оригинал, уменьшенный браузером;
- обработка живёт в `save()` модели, а не во вьюхе загрузки: путей загрузки
  несколько (страница галереи, форма поста, админка), и привязанная к
  одному из них она для остальных просто не выполнялась бы;
- обрабатывается только **новый** файл (признак — `FieldFile._committed`),
  иначе смена порядка картинок в посте пересжимала бы уже сжатое, теряя
  качество на каждом круге;
- анимация не трогается (пересохранение GIF оставило бы один кадр),
  прозрачность сохраняется (PNG с альфой не переводится в JPEG), а если
  обработка не дала выигрыша — остаётся оригинал;
- EXIF снимается, и это не косметика: `exif_transpose` применяет
  ориентацию, без которой снимки с телефона лежат на боку, а сам EXIF несёт
  GPS-координаты, которые в общей галерее ни к чему;
- одиночное фото в посте показывается оригиналом, а не миниатюрой: оно
  занимает всю ширину карточки, и 480 px там растянулись бы в мыло.

Проверено живьём: снимок 4000×3000 на 13.4 МБ лёг как 1440×1920 на 1.18 МБ
(в 11 раз меньше), развернулся по EXIF, миниатюра — 27 КБ, и страница
галереи грузит именно её.

**Новые модули, которые пишутся сразу на storage:** обменник, информационный
каталог, документы подразделений, вложения чата, приказы, файлы задач.

### 1.1.1. Порядок внедрения

Портал ещё не в проде, поэтому миграция обходится дёшево — но это не повод
начинать с неё. Правильный порядок:

1. Написать `storage` (модели, сервис, команды).
2. Написать **обменник** поверх него — первый потребитель, на котором нечего
   ломать.
3. Убедиться на нём, что дедупликация, `detach()`, `ORPHAN` и очистка по
   расписанию работают как задумано.
4. Только после этого мигрировать `posts.PostFile` и `phonebook.Phonebook`
   (раздел 11).

Причина такого порядка: на первом реальном потребителе почти наверняка
вскроется что-то, не предусмотренное в этом документе, и API немного
изменится. Дешевле поймать это на пустом модуле, чем переписывать уже
мигрированные посты второй раз.

### 1.2. Отклонённые варианты

- **`FileReference` (GenericForeignKey) как отдельная таблица связей** —
  отклонено. При наличии прямых `ForeignKey` из моделей-потребителей это
  второй источник истины об одном факте, то есть гарантированный источник
  рассинхронизации. Источник истины — сами FK.
- **Ref-count на файле** — отклонено: счётчик рассинхронизируется с
  реальностью при любой операции в обход сервиса (`bulk_create`,
  `queryset.delete()`, прямой SQL), и расхождение проявляется как молчаливая
  потеря данных. Аргумент «ref-count безопасен, если все операции идут через
  сервис» не выдерживает проверки: сервис не может создавать записи
  потребителей за них (у `ExchangeFile` свои обязательные поля — `owner`,
  `expires_at`, `folder`), значит FK всё равно создаёт потребитель, и забыть
  инкремент так же легко, как забыть что угодно ещё.
- **Явный реестр моделей-потребителей в settings** — отклонено (см. 5.2).
- **Метод `attach()`** — отклонён (см. 5.1).
- **Поле `visibility` на файле «просто как метаданные»** — отклонено. Поле,
  заведённое «не для проверки доступа», рано или поздно будет использовано
  именно для неё. Кроме того, при дедупликации оно неопределимо: один blob
  бывает приватным в чате и публичным в приказах одновременно. Видимость —
  свойство объекта-потребителя, там ей и место.

## 2. Модели

Ключевое решение: **содержимое и его именованное использование разделены на две
модели.** Одно и то же содержимое (`FileBlob`) может фигурировать в системе под
разными именами (`FileObject`): «Трудовой договор.docx» в отделе кадров и
«Договор Иванова.docx», отправленный в чате, — это один физический blob и два
`FileObject` с разными правами и разными сроками хранения.

Без этого разделения `unique(checksum)` на единственной модели сделал бы
невозможным хранение одного содержимого под двумя именами, а отказ от
`unique` — сделал бы дедупликацию негарантированной при конкурентных
аплоадах. Вводить это разделение миграцией позже, на заполненной БД, заметно
дороже, чем заложить сразу.

### `FileBlob` — физическое содержимое

```python
class FileBlob(models.Model):
    class Status(models.TextChoices):
        ACTIVE = 'active', 'Активен'
        ORPHAN = 'orphan', 'Без ссылок (ожидает удаления)'

    file = models.FileField(upload_to=blob_upload_path)
    checksum = models.CharField(max_length=64, unique=True)  # sha256, hex
    size = models.PositiveBigIntegerField()
    mime_type = models.CharField(max_length=100, blank=True)

    created_at = models.DateTimeField(auto_now_add=True)

    status = models.CharField(
        max_length=10, choices=Status.choices, default=Status.ACTIVE, db_index=True
    )
    orphaned_at = models.DateTimeField(null=True, blank=True)

    class Meta:
        indexes = [models.Index(fields=['status', 'orphaned_at'])]
```

- `checksum` — `unique=True`, а не просто индекс. Гарантирует дедупликацию даже
  при одновременных аплоадах одного содержимого: второй запрос получит
  `IntegrityError` и подхватит запись первого (см. 5.3).
- `blob_upload_path` кладёт файл в `storage/blobs/<checksum[:2]>/<checksum>` —
  путь определяется только содержимым, оригинальное имя в путь не входит.
- Статус жизненного цикла живёт здесь, а не на `FileObject`: с диска удаляется
  именно содержимое, когда на него не осталось ни одной ссылки.

### `FileObject` — именованный объект файла

```python
class FileObject(models.Model):
    class Category(models.TextChoices):
        CHAT = 'chat', 'Вложение чата'
        EXCHANGE = 'exchange', 'Обменник'
        DOCUMENT = 'document', 'Документ подразделения'
        CATALOG = 'catalog', 'Информационный каталог'
        TASK = 'task', 'Файл задачи'

    # related_name='file_objects', а не 'objects': последнее перекрыло бы
    # менеджер модели (FileBlob.objects) и сломало бы любой запрос к ней.
    blob = models.ForeignKey(FileBlob, on_delete=models.PROTECT, related_name='file_objects')
    original_name = models.CharField(max_length=255)
    category = models.CharField(max_length=20, choices=Category.choices, db_index=True)

    uploaded_by = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.SET_NULL, null=True, related_name='+'
    )
    uploaded_at = models.DateTimeField(auto_now_add=True)

    @property
    def size(self):
        return self.blob.size

    @property
    def mime_type(self):
        return self.blob.mime_type
```

- Модули-потребители ссылаются **на `FileObject`**, не на `FileBlob`.
- `category` определяет срок хранения (раздел 4).
- `uploaded_by` — информационное поле (кто произвёл аплоад), в проверке прав
  не участвует (раздел 8).
- Полей прав доступа здесь нет намеренно: после дедупликации одно содержимое
  может иметь несовместимые политики видимости одновременно.

**О названиях.** `FileBlob` — физическое содержимое (`8a72ff…pdf`),
`FileObject` — объект с именем и метаданными («Приказ №12 от 2026 года»). Это
стандартное для индустрии разделение blob/object; вариант `StoredFile` из
ранней редакции отброшен, так как не объяснял, чем отличается от `FileBlob`.

### `StorageAuditLog` — журнал операций

```python
class StorageAuditLog(models.Model):
    class Action(models.TextChoices):
        UPLOAD = 'upload', 'Загрузка'
        DETACH = 'detach', 'Отвязка ссылки'
        PURGE = 'purge', 'Физическое удаление'
        RESTORE = 'restore', 'Восстановление из ORPHAN'

    action = models.CharField(max_length=20, choices=Action.choices)
    checksum = models.CharField(max_length=64, db_index=True)
    original_name = models.CharField(max_length=255, blank=True)
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.SET_NULL, null=True, related_name='+'
    )
    consumer = models.CharField(max_length=100, blank=True)  # 'exchange.ExchangeFile'
    created_at = models.DateTimeField(auto_now_add=True, db_index=True)
```

Журнал хранит `checksum` строкой, а не FK на `FileBlob` — чтобы записи
переживали физическое удаление blob'а и отвечали на вопрос «кто и когда удалил
файл, которого больше нет». Для портала с приказами и документами
подразделений это требование, а не пожелание.

### Модели-потребители

```python
# apps/exchange/models.py
class ExchangeFolder(models.Model):
    """Подпапка внутри личной папки сотрудника (например, "Проект Альфа"
    внутри папки Иванова). Дерево через self-FK, как CatalogFolder."""
    name = models.CharField(max_length=255)
    owner = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name='exchange_folders')
    parent = models.ForeignKey('self', on_delete=models.CASCADE, null=True, blank=True, related_name='children')
    created_by = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.SET_NULL, null=True, related_name='+')


class ExchangeFile(models.Model):
    file_object = models.ForeignKey('storage.FileObject', on_delete=models.PROTECT, related_name='+')
    owner = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name='exchange_files')
    folder = models.ForeignKey(ExchangeFolder, on_delete=models.CASCADE, null=True, blank=True, related_name='files')
    uploaded_by = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.SET_NULL, null=True, related_name='+')
    uploaded_at = models.DateTimeField(auto_now_add=True)

    # Корзина (раздел 6)
    is_deleted = models.BooleanField(default=False, db_index=True)
    deleted_at = models.DateTimeField(null=True, blank=True)
    deleted_by = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.SET_NULL, null=True, blank=True, related_name='+'
    )
```

Полный список потребителей: `exchange.ExchangeFile`,
`catalog.CatalogDocument`, `deptdocs.DepartmentDocument`, `posts.PostFile`,
`phonebook.Phonebook` (два поля — оригинал и PDF-копия, раздел 13) и
`profiles.MessageAttachment` — вложение личного сообщения. Последнее
заведено своей моделью, а не через `MessageModel.file` из
django_private_chat2: там обычный `FileField` в общей медиатеке, то есть
файл доступен любому, кто знает адрес, не дедуплицируется и лежит вечно.
У `MessageAttachment` `file_object` **nullable** — по истечении срока
(раздел 4) поле обнуляется, а имя и размер остаются, чтобы пузырь в
переписке мог объяснить, куда делся файл.

`on_delete=PROTECT` на `file_object` намеренно: `FileObject` не должен
исчезать каскадом от потребителя, иначе не соблюдается отложенное удаление
(раздел 7) и не пишется аудит. Обратное направление — когда каскад сносит
саму запись `ExchangeFile` (например, при удалении пользователя-владельца
папки, или подпапки, в которой лежал файл) — закрыто автоматическим
`detach()` через `post_delete` (5.5).

**Подпапки обменника (`ExchangeFolder`).** Список *корневых* папок по-прежнему
равен списку сотрудников (раздел 1.1 не поменялся) — `ExchangeFolder` не
самостоятельная папка, а вложенность внутри чьей-то личной папки, поэтому у
неё обязателен `owner`. `ExchangeFile.folder=None` означает файл прямо в
корне личной папки владельца, как было до появления подпапок.

Права на подпапки такие же открытые, как и на файлы: создать подпапку в
чужой личной папке может любой сотрудник — так же, как положить туда файл
(`CreateExchangeFolderView` не проверяет владельца из URL). Удалять может
владелец личной папки или тот, кто создал подпапку (`ExchangeFolder.can_be_deleted_by`,
тот же принцип, что и в `ExchangeFile.can_be_deleted_by`). Первая редакция
ошибочно ограничивала создание/удаление только владельцем — по аналогии с
`deptdocs.DepartmentFolder`, где папку заводит кто угодно, но управляет ею
только список `allowed_users`. Это противоречило открытой природе
обменника: пользователь не мог создать подпапку в чужой папке и не видел
кнопки управления там, где мог загружать файлы. Исправлено — модель прав
подпапок полностью совпадает с моделью прав файлов. Видимость содержимого
не менялась изначально: все файлы обменника видны всем сотрудникам,
вложенность меняет только организацию, не права.

**Перенос между личными папками = смена владельца.** Первая редакция
переносить файл или подпапку в личную папку другого сотрудника запрещала:
`MoveExchangeFileView` требовала, чтобы папка назначения принадлежала
владельцу файла. Причина была записана — чужой файл, появившийся в личной
папке, выглядит для её владельца как подмена содержимого без
предупреждения. Запрет снят решением владельца портала, и он действительно
расходился с остальным обменником: положить файл в чужую папку
**загрузкой** было можно с самого начала, а запрет на перенос заставлял
делать то же самое в два действия — скачать и загрузить заново, создав
второй `FileObject` там, где хватало смены папки.

Перенос в чужую папку меняет `owner`, а не только `folder`. Это не выбор
удобства, а требование модели: список файлов фильтруется по `owner` и
`folder` одновременно (`ExchangeFolderView`), поэтому файл со старым
владельцем в новой папке не был бы виден вообще нигде — ни в исходной
папке, ни в целевой. Отсюда три следствия, принятые явно:

- **право удаления переходит вместе с владельцем.** `can_be_deleted_by` —
  это владелец папки или загрузивший, значит прежний владелец право
  теряет, а загрузивший сохраняет и может вернуть файл обратно;
- **владелец папки-назначения уведомляется** тем же
  `Notification.Kind.FILE_SHARED`, что и при загрузке: для него разницы
  между «положили файл» и «перенесли файл» нет;
- **перенос подпапки меняет владельца всего поддерева** — вложенных папок
  и файлов в них, включая лежащие в корзине: у тех `folder` сохранён, и
  восстановление вернёт файл именно в переехавшую папку.

Квоты это не касается: квота считается по `FileObject.uploaded_by`
(раздел 9), а перенос `ExchangeFile` объектов storage не трогает вовсе —
место остаётся за тем, кто файл загрузил.

Куда переносить, спрашивает одна модалка — общая для файлов, папок и
массового переноса. Список в ней — личные папки всех сотрудников с их
подпапками (`exchange.views._move_targets`, отступы считает общий
`storage.utils.build_folder_choices`). Корень личной папки — не
`ExchangeFolder`, а сам сотрудник, поэтому назначение задаётся парой
`owner_id` + `folder_id`: одним id корень не назвать. Владельца определяет
подпапка, если она указана, — она всегда знает, в чьей личной папке
заведена; пара «личная папка одного + подпапка другого» отвергается 404.

## 3. Размещение на диске

```
media/
    storage/
        blobs/
            ab/
                abcdef0123…        ← живые файлы, имя = checksum
```

- **`blobs/`** — единственное место, где лежат файлы. Имя файла равно
  checksum, поэтому одинаковое содержимое физически не дублируется.
- Отдельного `temp/` **нет**. Ранняя редакция документа предполагала запись
  в `temp/` с последующим `os.replace` в `blobs/`, но в реализации это
  оказалось лишним слоем: Django к моменту вызова `upload()` уже полностью
  приняла загрузку (в память или во временный файл), а `FileSystemStorage`
  сам пишет через временный файл с последующим переименованием. Расхождения
  диска и БД всё равно возможны при аварийном завершении процесса — их ловит
  `storage_verify` (5.4).
- Отдельного `trash/` **нет**: корзина реализована на уровне
  модуля-потребителя (раздел 6), файл при удалении физически никуда не
  переезжает.
- `media/storage/` **не должен раздаваться как обычная медиатека** — иначе
  проверка прав обходится прямой ссылкой вида
  `/media/storage/blobs/<checksum>`. Закрыто на двух уровнях: в корневом
  `urls.py` перехватчик `^media/storage/` возвращает 404 до общего
  `static()`-обработчика, и в проде дополнительно
  `location /media/storage/ { deny all; }` в nginx. Уровни не дублируют друг
  друга, а закрывают разные режимы: перехватчик в `urls.py` работает только
  когда медиа раздаёт Django (`DEBUG=True`), в проде до него дело не доходит
  вовсе. Регрессионные тесты — `storage/tests/test_direct_access.py`
  (Django-уровень) и `storage/tests/test_x_accel_redirect.py`
  (заголовок и конфиг nginx).

## 4. Категории и сроки хранения

Срок жизни задаётся централизованно по категории, а не разрозненными
настройками в каждом модуле:

```python
# settings.py — значения по умолчанию
STORAGE_CATEGORY_TTL = {
    'chat': 7,         # дней
    'exchange': 7,
    'task': 90,
    'document': None,  # бессрочно
    'catalog': None,   # бессрочно
}
```

Сроки категорий «чат» и «обменник» правятся в админке (раздел 9): это
эксплуатационное решение — сколько дней держать чужие файлы, решает
администратор портала, а не разработчик. У каталога и документов отделов
поля в админке нет намеренно: срока хранения у них не бывает, а поле
обещало бы удаление, которого никто не выполняет.

**Применяет TTL сам модуль-потребитель, а не storage.** `storage` отдаёт
только политику — `StorageService.get_category_ttl_days(category)`. Задача
удаления живёт в потребителе, потому что только он знает, что значит
«просроченная запись» в его предметной области: см.
`exchange.tasks.cleanup_expired_exchange_files`, которая удаляет
`ExchangeFile` старше срока и затем зовёт `detach()`, и
`profiles.tasks.cleanup_expired_chat_attachments` — та же схема для
вложений переписки, с одной разницей: запись вложения не удаляется, у неё
только обнуляется `file_object`. Иначе на месте вложения в переписке
оказался бы пустой пузырь без единого следа того, что файл вообще был.

Собственной задачи «удалить всё истёкшее» у storage намеренно **нет**. Такая
задача (была в ранней редакции как `purge_expired_objects`) вызывала
`detach()` для `FileObject`, на который ещё ссылается живая запись
потребителя. `detach()` такие файлы защищает и не удаляет ничего — но
счётчик всё равно рапортовал об успехе, то есть очистка молча не работала.
Удалять же чужие записи storage не может: он не знает бизнес-логику
потребителей.

**Про дедупликацию отдельного правила не требуется.** Один blob может быть
одновременно вложением чата (TTL 7 дней) и документом каталога (бессрочно).
Когда истекает срок чат-вложения, удаляется только его `FileObject`; blob
уходит в `ORPHAN` лишь если на него не осталось **ни одной** ссылки — эту
проверку уже делает `detach()` (5.2). Отдельно вычислять «максимальный TTL по
всем ссылающимся объектам», как предполагала ранняя редакция, не нужно:
инвариант обеспечивается на уровне подсчёта ссылок.

## 5. Сервисный слой — `StorageService`

`storage/services.py` — единственная точка входа. Модули-потребители не
работают с `FileBlob`/`FileObject.objects` напрямую и не трогают файловую
систему.

```python
class StorageService:
    @staticmethod
    def upload(uploaded_file, *, user, category) -> FileObject: ...

    @staticmethod
    def detach(file_object: FileObject, *, user=None, consumer='') -> None: ...

    @staticmethod
    def get_download_response(
        file_object: FileObject, request, *, inline: bool = False
    ) -> HttpResponse: ...

    @staticmethod
    def get_usage(user) -> int: ...

    @staticmethod
    def get_category_ttl_days(category) -> int | None: ...

    @staticmethod
    def purge_expired_orphans() -> int: ...

    @staticmethod
    def find_untracked_files() -> list[str]: ...
```

`inline=True` в `get_download_response()` отдаёт файл с
`Content-Disposition: inline` вместо `attachment` — нужно там, где документ
показывается прямо в браузере, а не скачивается (PDF справочника в
`<iframe>`, см. `phonebook.views.PhonebookViewFileView`).

### 5.1. Почему нет `attach()`

Ранний вариант API требовал от потребителя вызвать `attach()` после создания
своей FK-записи. Это API, приглашающее к ошибке: забыть вызов легко, а
последствие отложено на неделю и проявляется как «пропал файл» без видимой
связи с причиной.

Вместо этого `upload()` **всегда** возвращает `FileObject`, чей blob находится
в `ACTIVE`: если по checksum нашёлся blob в `ORPHAN`, `upload()` сам
возвращает его в `ACTIVE` внутри своей транзакции. Потребителю остаётся один
метод — `detach()` при удалении. Меньше API — меньше способов ошибиться, и
удаление обычно пишут внимательнее, чем создание.

Вариант «сервис сам создаёт запись потребителя» (`create_reference()`) тоже
отклонён: у моделей-потребителей свои обязательные поля, которые storage знать
не должен, иначе он превращается в модуль, зависящий от всех остальных.

### 5.2. Как определяется «ссылок больше нет»

Без реестра в settings — потребители находятся интроспекцией:

```python
def _iter_consumer_fields():
    for model in apps.get_models():
        if model._meta.app_label == 'storage':
            continue
        for field in model._meta.concrete_fields:
            if field.is_relation and field.related_model is FileObject:
                yield model, field.name


def _object_has_references(file_object) -> bool:
    for model, field_name in _iter_consumer_fields():
        if model._default_manager.filter(**{field_name: file_object}).exists():
            return True
    return False
```

**Важно: обходить нужно `apps.get_models()`, а не
`FileObject._meta.get_fields()`.** Первая реализация искала обратные связи
через `get_fields()` и была нерабочей: все потребители объявляют FK с
`related_name='+'`, который подавляет создание обратной связи, поэтому
`get_fields()` не возвращал по ним ничего и проверка **всегда** давала
`False`. От тихой потери данных спасал только `on_delete=PROTECT`,
превращавший баг в `ProtectedError` (500 у пользователя) вместо удаления
используемого файла. Регрессия закрыта тестами
`storage/tests/test_references.py`, включая проверку, что все пять
потребителей действительно находятся.

Строковый список моделей в settings отклонён: его легко забыть обновить при
добавлении нового потребителя, ни один тест на это не упадёт, а последствие —
молчаливое удаление используемых файлов. Интроспекция не требует ручной
синхронизации в принципе.

Если в будущем появятся служебные модели со ссылкой на `FileObject`, которые
не должны считаться «использованием» (архивы, история изменений), они
исключаются одним предикатом в `_iter_consumer_fields()` — в отличие от
ref-count, где та же ситуация требует не забыть инкремент в каждом новом месте.

### 5.3. Транзакции и гонки

Три места требуют явной блокировки, иначе возможна потеря данных:

**`upload()` — воскрешение из ORPHAN.** Без блокировки cleanup может удалить
файл с диска между проверкой статуса и коммитом, и пользователь получит
успешный аплоад несуществующего файла:

```python
@transaction.atomic
def upload(uploaded_file, *, user, category):
    _validate_size_and_quota(uploaded_file, user)
    checksum = _sha256(uploaded_file)

    # Ключевой момент: select_for_update() блокирует СУЩЕСТВУЮЩУЮ строку, но
    # если blob'а с этим checksum ещё нет — блокировать нечего, и два
    # параллельных upload() одинакового нового содержимого оба увидят None,
    # оба запишут файл на диск, и лишь один словит IntegrityError. На диске
    # останутся дубликаты с суффиксами от FileSystemStorage. Advisory lock
    # по checksum сериализует именно эту гонку — ДО появления строки.
    _acquire_checksum_lock(checksum)   # pg_advisory_xact_lock

    blob = FileBlob.objects.select_for_update().filter(checksum=checksum).first()
    if blob:
        if blob.status == FileBlob.Status.ORPHAN:
            blob.status = FileBlob.Status.ACTIVE
            blob.orphaned_at = None
            blob.save(update_fields=['status', 'orphaned_at'])
            _audit(Action.RESTORE, checksum=checksum, user=user)
    else:
        try:
            # Вложенный atomic() = savepoint. Без него IntegrityError
            # помечает всю транзакцию Postgres «испорченной», и следующий
            # же SELECT падает с TransactionManagementError вместо штатной
            # обработки гонки.
            with transaction.atomic():
                blob = FileBlob.objects.create(
                    file=File(uploaded_file, name=checksum),
                    checksum=checksum, size=uploaded_file.size, mime_type=mime_type,
                )
            _audit(Action.UPLOAD, checksum=checksum, user=user)
        except IntegrityError:
            # Страховка на случай бэкенда без advisory lock.
            blob = FileBlob.objects.select_for_update().get(checksum=checksum)

    return FileObject.objects.create(
        blob=blob, original_name=uploaded_file.name, category=category, uploaded_by=user,
    )
```

**`detach()` — проверка оставшихся ссылок.** Вся операция в одной транзакции с
блокировкой blob'а, иначе между проверкой разных моделей может появиться новая
ссылка:

```python
@transaction.atomic
def detach(file_object, *, user=None, consumer=''):
    blob = FileBlob.objects.select_for_update().get(pk=file_object.blob_id)
    _audit(Action.DETACH, blob, user, consumer, file_object.original_name)

    if _has_references(file_object):
        return

    file_object.delete()

    if not blob.file_objects.exists():
        blob.status = FileBlob.Status.ORPHAN
        blob.orphaned_at = timezone.now()
        blob.save(update_fields=['status', 'orphaned_at'])
```

**`purge_expired_orphans()` — повторная проверка внутри транзакции.** Статус
обязательно перечитывается под блокировкой непосредственно перед удалением
файла — между выборкой кандидатов и удалением blob мог быть воскрешён:

```python
def purge_expired_orphans():
    deadline = timezone.now() - timedelta(days=settings.STORAGE_ORPHAN_RETENTION_DAYS)
    candidates = FileBlob.objects.filter(status=FileBlob.Status.ORPHAN, orphaned_at__lte=deadline)

    purged = 0
    for blob_id in list(candidates.values_list('pk', flat=True)):
        with transaction.atomic():
            blob = FileBlob.objects.select_for_update().filter(pk=blob_id).first()
            # Перечитываем статус под блокировкой: за время цикла blob мог
            # вернуться в ACTIVE через upload().
            if not blob or blob.status != FileBlob.Status.ORPHAN:
                continue
            if blob.orphaned_at > deadline or blob.file_objects.exists():
                continue

            _audit(Action.PURGE, blob, user=None)
            blob.file.delete(save=False)
            blob.delete()
            purged += 1
    return purged
```

### 5.4. Сверка диска и БД

Файл пишется на диск внутри транзакции, поэтому её откат (или аварийное
завершение процесса) может оставить файл, о котором БД не знает. Механизм
`ORPHAN` его не найдёт по определению — он работает по записям `FileBlob`.

`find_untracked_files()` обходит `MEDIA_ROOT/storage/blobs/` и возвращает
пути, для которых нет `FileBlob` с соответствующим checksum. Запускается
редко (раз в месяц) командой `storage_verify --delete-untracked`, по
умолчанию — только отчёт, без удаления.

**Тесты обязаны писать в свой `MEDIA_ROOT`.** Это не удобство, а условие
работоспособности самой сверки. Django создаёт и удаляет тестовую БД, но
файловую систему за собой не убирает: пока `MEDIA_ROOT` под тестами
совпадал с боевым, каждый прогон оставлял blob'ы в `media/storage/blobs/`
навсегда — записи `FileBlob` исчезали вместе с тестовой базой, файлы нет.
Накопилось 2887 файлов при 25 записях в БД, то есть `storage_verify`
рапортовал бы о 2862 «потерянных» файлах, и настоящее расхождение,
ради которого он и заведён, утонуло бы в этом шуме.

Тот же механизм ломал и дедупликацию внутри прогона: имя файла равно
checksum, поэтому на следующем тесте (БД откатилась, файл остался)
`FileSystemStorage` находил файл существующим и дописывал случайный
суффикс — `<checksum>_B24AkEu`. Одного содержимого так накапливалось до
300 копий.

Закрыто в `settings.py` (`MEDIA_ROOT` во временный каталог под
`'test' in sys.argv`), а тесты, проверяющие состояние диска, берут свой
каталог на каждый тест — иначе файл от предыдущего теста переживает
откат БД и делает проверку недостоверной. Стережёт это
`test_deduplication.TestMediaIsolationTest`.

### 5.5. Автоматический `detach()` при удалении записи потребителя

Требовать от потребителя ручной вызов `detach()` после удаления своей записи
достаточно ровно до первого `ForeignKey` с `on_delete=CASCADE`. Каскад сносит
запись сам, и вызвать `detach()` в этот момент некому.

В проекте таких путей четыре, и ни один не является нарушением дисциплины —
их никто не пишет, они срабатывают сами:

| Каскад | Что сносит |
|---|---|
| `CatalogFolder` → `CatalogDocument` | удаление папки каталога |
| `DepartmentFolder` → `DepartmentDocument` | удаление папки документов отдела |
| `*Folder.parent` → `self` | удаление дерева папок целиком |
| `User` → `ExchangeFile` (`owner`) | удаление уволенного сотрудника |

Последствие пропущенного `detach()` тихое и необратимое: blob остаётся
`ACTIVE` без единой ссылки. Механизм `ORPHAN` его не найдёт (статус не
сменился), `purge_expired_orphans()` не тронет, а `find_untracked_files()`
не сочтёт потерянным — запись `FileBlob` на месте и файл на диске тоже.
Такой blob живёт вечно, то есть ровно та проблема, ради которой storage и
писался.

Поэтому `detach()` при удалении строки потребителя выполняется
**автоматически** — сигналом `post_delete` (`storage/signals.py`),
подключённым ко всем моделям с FK на `FileObject` той же интроспекцией, что
и в 5.2. Регистрировать потребителя не нужно, забыть вызов невозможно.

**Атрибуция.** Сигнал не знает, кто инициировал удаление, а `StorageAuditLog`
обязан отвечать на вопрос «кто удалил файл» (раздел 2). Поэтому вызывающий
код помечает объект перед `delete()`:

```python
from storage.signals import attribute_deletion

attribute_deletion(document, user=request.user, consumer='catalog.CatalogDocument')
document.delete()          # detach() выполнит сигнал, журнал получит инициатора
```

Без пометки удаление записывается как каскадное: `user=None`, `consumer` с
суффиксом `:cascade`. Это не ошибка, а честная запись «файл удалён вместе с
владельцем, конкретного инициатора не было».

Пометка живёт на экземпляре в памяти, поэтому работает только при удалении
**самого помеченного объекта**. При каскаде Django создаёт собственные
экземпляры, и пометки на них не будет — если атрибуция важна, удаляйте
записи явно до того, как их снесёт каскад (так сделано в
`posts.PostDeleteView`: вложения удаляются до поста).

**`StorageService.detach()` остаётся публичным API** — для случая, когда
ссылка снимается *без* удаления строки: `phonebook` подменяет `file_object`
на живой записи при замене файла справочника, и никакого `post_delete` там
не происходит. Повторный вызов безопасен: если `FileObject` уже удалён,
`detach()` выходит сразу, не дублируя запись в журнале и не сбрасывая
`orphaned_at`.

Регрессионные тесты — `storage/tests/test_cascade.py` (все четыре каскадных
пути) и `storage/tests/test_consumers.py` (окончательное удаление у каждого
потребителя плюс сохранение атрибуции).

## 6. Корзина

Корзина — **функция модуля-потребителя, не storage**. Причина: пользователь
восстанавливает документ с его именем, папкой, правами и местом в каталоге, а
не абстрактный blob. Если запись `DepartmentDocument` физически удалена,
воскрешение blob'а не даёт ничего — восстанавливать нечего.

Схема:

```
Пользователь удалил документ
        │
        ▼
  is_deleted = True, deleted_at = now()      ← объект в корзине,
  detach() НЕ вызывается                       blob остаётся ACTIVE
        │
        ├──── восстановление: is_deleted = False  ──▶ ничего больше не нужно,
        │                                              файл никуда не девался
        ▼
  очистка корзины (по сроку или вручную)
        │
        ▼
  реальное удаление записи + StorageService.detach()
        │
        ▼
  дальше — обычный жизненный цикл blob'а (раздел 7)
```

- Пока объект в корзине, `detach()` не вызывается вообще — никаких новых
  состояний в `FileBlob` для этого не требуется.
- Списки/выдача в модуле-потребителе фильтруются по `is_deleted=False`;
  удобно оформить менеджером по умолчанию, чтобы забыть фильтр было сложнее.
- `ORPHAN` (раздел 7) — **не корзина**, а техническое состояние «на содержимое
  не осталось ссылок». Он защищает от потери файла при повторной загрузке того
  же содержимого, но не заменяет пользовательское восстановление.

### 6.1. Автоочистка корзины по сроку

До появления этого механизма корзина чистилась только вручную по одному
файлу — записи с `is_deleted=True` лежали в БД неограниченно, пока кто-то не
заходил и не жал «удалить окончательно» на каждой отдельно.

Срок — `STORAGE_TRASH_RETENTION_DAYS` (сейчас 30 дней), задача-обёртка живёт
у каждого потребителя своя: `catalog.tasks.cleanup_catalog_trash`,
`deptdocs.tasks.cleanup_deptdocs_trash`. Тот же принцип, что и в разделе 4
для TTL по категориям — storage не может чистить чужие таблицы, он не знает
бизнес-логику потребителя. Расписание заводится дата-миграциями
(`catalog/migrations/0002_seed_trash_cleanup_task.py`,
`deptdocs/migrations/0003_seed_trash_cleanup_task.py`) по тому же образцу,
что и `storage/migrations/0002_seed_periodic_tasks.py`.

**У обменника отдельной задачи нет.** `exchange.tasks.cleanup_expired_exchange_files`
уже удаляет записи по TTL от `uploaded_at` (7 дней), **включая те, что в
корзине** — попадание в корзину не продлевает жизнь файла, иначе обменник
можно засорить, просто ничего не восстанавливая. TTL строже срока хранения
корзины, поэтому вторая задача была бы избыточной: до 30-дневного порога
корзины запись не доживает.

Ручной запуск раньше расписания — `StorageDashboardView` /storage/`:
кнопка «Очистить сейчас» на карточке корзины, доступна только персоналу
(`is_staff`), потому что массовая очистка задевает записи всех
пользователей, а не только свои. Там же — общая сводка занятого места
(`StorageService.get_storage_stats()`) и своя квота (`get_usage()`).

### 6.2. Единая страница корзины

`/storage/trash/` (`UnifiedTrashView`) показывает корзины всех трёх
потребителей на одной странице с табами вместо трёх разных адресов
(`/exchange/trash/`, `/catalog/trash/`, `/deptdocs/trash/`). Причина:
внешне все три корзины неотличимы — тот же layout `fm-scope`, тот же
заголовок «Корзина» в хлебной крошке — и легко открыть корзину не того
модуля, решив, что удалённый файл пропал, хотя он лежит в корзине другого
раздела.

Вьюха не дублирует логику отдельных `TrashView` — она использует те же
правила видимости для каждого queryset (обменник: моя папка или моё
удаление; каталог: всё, он общедоступен; приватный доступ: только папки,
где я в `allowed_users`) и переиспользует существующие карточки
(`exchange_file_card.html`, `catalog_document_card.html`, `deptdoc_card.html`
с `is_trash=True`). Кнопки восстановить/удалить окончательно шлют запросы
на те же эндпоинты модулей, что и раньше — страница только собирает
представление, не меняет бизнес-логику.

Табы переключаются на клиенте (Alpine, `x-show`) без перезагрузки —
`?tab=` в URL задаёт таб по умолчанию при заходе (используется ссылками
из `StorageDashboardView`, где на каждой карточке «Открыть корзину» ведёт
сразу в нужный таб).

Страница показывает **последние N записей каждого таба**
(`TRASH_PREVIEW_LIMIT`), а не всё содержимое: корзина каталога общая для
всего портала, и без ограничения эта страница рендерила бы все удалённые
документы разом — у отдельных `TrashView` каждого модуля `paginate_by`
был, а у сводной не было. При превышении лимита выводится ссылка на
корзину конкретного модуля, где работает обычная пагинация.

Счётчики на карточках `StorageDashboardView` считают **ровно то, что
пользователь увидит в корзине**. Ранняя редакция показывала по обменнику
число удалённых файлов всех пользователей, тогда как корзина обменника
показывает только свои — карточка обещала «12 файлов», а внутри
оказывалось два.

Старые адреса отдельных корзин (`exchange_trash`, `catalog_trash`,
`deptdocs_trash`) не удалены — работают как есть, `fm_menu.html` теперь
ссылается на `storage_trash`.

## 7. Жизненный цикл содержимого и правила удаления

```
    StorageService.upload()
            │
            ▼
      ┌──────────┐   detach(): ссылок на blob не осталось   ┌────────┐
      │  ACTIVE  │ ─────────────────────────────────────────▶│ ORPHAN │
      └──────────┘                                           └────────┘
            ▲                                                     │
            │  upload() нашёл тот же checksum → RESTORE           │  спустя
            └─────────────────────────────────────────────────────┤  N дней
                                                                  ▼
                                              purge: файл с диска + запись FileBlob
                                              (запись в StorageAuditLog остаётся)
```

- **ACTIVE → ORPHAN** — синхронно внутри `detach()`, когда удалён последний
  `FileObject`, ссылающийся на blob. Сам `detach()` при удалении записи
  потребителя вызывается автоматически сигналом `post_delete` (5.5), в том
  числе когда запись сносит каскад.
- **ORPHAN → ACTIVE** — внутри `upload()`, если то же содержимое загружено
  повторно до истечения срока.
- **ORPHAN → удалён** — задача `storage.tasks.cleanup_orphan_files` (обёртка
  над `StorageService.purge_expired_orphans()`), ежедневно через **Celery
  beat**. Расписание хранится в БД (`django_celery_beat`), а не в конфиге ОС:
  разработка идёт на Windows, прод — на Astra Linux, и вариант «Task
  Scheduler здесь, cron там» означал бы два разных набора конфигурации.
  Первичное расписание заводится дата-миграцией
  `storage/migrations/0002_seed_periodic_tasks.py`, дальше правится через
  `/admin/` без деплоя. Брокер — тот же Redis, что и для Channels, но
  отдельная логическая база (`db=1`).
- Прямой `FileBlob.delete()` в обход сервиса не используется нигде: он оставит
  файл на диске (Django не удаляет файлы при удалении записи) и не запишет
  аудит.

Периодические задачи (Celery beat, расписание в `/admin/`):

| Задача | Периодичность | Что делает |
|---|---|---|
| `storage.tasks.cleanup_orphan_files` | ежедневно | физически удаляет blob'ы, пробывшие в `ORPHAN` дольше `STORAGE_ORPHAN_RETENTION_DAYS` |
| `storage.tasks.storage_verify` | ежемесячно | сверка диска и БД (5.4), по умолчанию только отчёт |
| `exchange.tasks.cleanup_expired_exchange_files` | ежедневно | удаляет файлы обменника старше TTL категории и зовёт `detach()` (раздел 4) |
| `catalog.tasks.cleanup_catalog_trash` | ежедневно | удаляет документы каталога из корзины старше `STORAGE_TRASH_RETENTION_DAYS` (6.1) |
| `deptdocs.tasks.cleanup_deptdocs_trash` | ежедневно | то же для документов отдела (6.1) |

Задачи storage продублированы management-командами (`cleanup_orphan_files`,
`storage_verify`) — удобно для ручного прогона и отладки без Celery.

## 8. Проверка прав и отдача файлов

**storage не хранит и не проверяет права доступа.** После дедупликации одно
содержимое может иметь несовместимые политики видимости в разных местах
использования, поэтому единая политика на уровне файла логически невозможна.

1. Модуль-потребитель реализует свою логику доступа обычными средствами
   (участник диалога, состоит в отделе `Category`, входит в
   `allowed_departments` документа и т.д.).
   Политика может быть и пустой: **в каталоге проверок нет намеренно** —
   см. «Каталог открыт на запись» ниже.
2. View потребителя сначала проверяет права **на свой объект**, и только затем
   вызывает `StorageService.get_download_response(...)`.
3. `storage` не публикует URL вида `/storage/file/<id>/` — скачать файл можно
   только через view модуля-потребителя. Это исключает обход прав прямой
   ссылкой.

### Каталог открыт на запись — это решение, а не пропуск

Ни одна пишущая вьюха `catalog` не проверяет прав: любой аутентифицированный
переименовывает, переносит, кладёт в корзину, восстанавливает и удаляет
окончательно любой документ, а также удаляет папку вместе с поддеревом.
Подтверждено владельцем портала 14.08.2026: каталог — общий рабочий раздел
организации, и разделение прав в нём не нужно.

Отличие от соседей ровно в этом: `exchange` проверяет
`can_be_deleted_by()`, `deptdocs` — `is_accessible_by()`, `catalog` не
проверяет ничего. Аудит такое место находит каждый раз, поэтому: **это не
дыра, чинить не нужно**. Единственная страховка от случайности —
подтверждение в интерфейсе и корзина (раздел 6): удаление документа
обратимо 30 дней.

### Отдача файлов

`get_download_response()` не пропускает файл через процесс Django в проде:

- **прод**: ответ с заголовком `X-Accel-Redirect` на внутренний
  (`internal`) nginx-location плюс `Content-Disposition` с `original_name` из
  `FileObject` — пользователь получает осмысленное имя, хотя на диске файл
  лежит под именем-хэшем;
- **разработка** (`DEBUG=True`): `FileResponse`, чтобы не требовать nginx
  локально.

```nginx
# Внутренний location для X-Accel-Redirect.
# alias — именно MEDIA_ROOT, а не .../storage/blobs/:
# get_download_response() считает путь относительно MEDIA_ROOT и отдаёт
# заголовок вида /protected/storage/blobs/ab/<checksum>. С alias на
# blobs/ путь удвоился бы (media/storage/blobs/storage/blobs/...).
location /protected/ {
    internal;
    alias /path/to/media/;
}

# ОБЯЗАТЕЛЬНО: закрыть прямой доступ к blob'ам.
# Перехватчик ^media/storage/ в корневом urls.py работает только когда
# медиа раздаёт Django, то есть при DEBUG=True. Как только перед
# приложением встаёт nginx с обычным `location /media/`, файл скачивается
# по прямой ссылке /media/storage/blobs/<checksum> в обход всех проверок
# прав модуля-потребителя.
location /media/storage/ {
    deny all;
}
```

**Где живёт этот конфиг.** Канонический вариант — `deploy/nginx/portal.conf`,
он в git. Локальный Windows-nginx (`nginx-1.28.0/conf/nginx.conf`) — копия с
путями этой машины, и весь его каталог в `.gitignore`: правка только там
никуда, кроме одного компьютера, не уезжает, а прод разворачивается из
репозитория. Оба файла проверяет `storage/tests/test_x_accel_redirect.py` —
он же ловит и обратную ошибку, когда прямой доступ закрывают, удалив
`location /media/` целиком (аватары и картинки постов лежат вне storage и
обязаны раздаваться по-прежнему, см. 1.1).

**Имя файла в `Content-Disposition` оформляется по RFC 5987**
(`filename*=utf-8''<percent-encoded>`), а не подставляется как есть.
`HttpResponse` кодирует значение заголовка вне latin-1 по RFC 2047
(`=?utf-8?b?…?=`) — форма, которой `Content-Disposition` не знает: браузер
сохранил бы файл под base64-строкой или под именем-хэшем из URL. Имена в
портале почти все кириллические, то есть это задевало бы почти каждое
скачивание — и только на проде, потому что в ветке `DEBUG` заголовок
собирает `FileResponse`, который делает это правильно сам.

Прод-путь через `X-Accel-Redirect` — не преждевременная оптимизация «для
больших систем»: портал работает на Daphne/ASGI, где отдача файла через воркер
занимает его на всё время скачивания. Десяток пользователей, тянущих по
100 МБ, забьют пул воркеров, и портал начнёт тормозить целиком, включая
WebSocket-чат. Стоимость решения — несколько строк кода и один `location` в
конфиге.

### 8.1. Массовая выгрузка одним архивом

`StorageService.get_archive_response()` — единственное место, где содержимое
файлов идёт **через процесс Django**. Иначе и быть не может: архива нет на
диске, `X-Accel-Redirect` на несуществующий файл не сошлёшь. Отсюда все
остальные решения в этом механизме.

**Сборка на лету, а не в память или во временный файл.** `zipfile` пишет в
`_ZipStreamBuffer` — объект, который ничего не хранит: генератор забирает
накопленное после каждого прочитанного чанка и отдаёт наружу. Память не
растёт с размером архива. Вариант «собрать и отдать» означал бы сотню
мегабайт на каждый параллельный запрос, вариант «собрать во временный
файл» — место на диске, уборку за собой и задержку первого байта до конца
сборки.

Ключевая деталь реализации: у буфера есть `tell()`, но **намеренно нет**
`seek()`. По отсутствию `seek()` `zipfile` понимает, что поток
неперемотываемый, и записывает размер и CRC в data descriptor *после*
содержимого, вместо того чтобы возвращаться и править уже отданный
заголовок. Появись у буфера `seek()` — архив собирался бы с враньём в
заголовках. Стережёт это `test_bulk_download.test_archive_is_readable_although_built_on_an_unseekable_stream`.

**`ZIP_STORED`, без сжатия.** Содержимое портала — pdf/docx/xlsx и
картинки, то есть уже сжатые форматы: deflate дал бы единицы процентов и
стоил бы процессорного времени того самого воркера, который в это время
держит соединение.

**Пределы обязательны** (`STORAGE_ZIP_MAX_FILES`,
`STORAGE_ZIP_MAX_TOTAL_SIZE`). Один запрос занимает воркер на всё время
выгрузки, поэтому «выделить всё в общем каталоге и скачать» без ограничения
было бы самообслуживаемым отказом портала. Превышение — `ArchiveTooLargeError`
с текстом причины, а не молчаливое усечение списка.

**Два режима одного адреса: `?check=1` и сам архив.** За архивом браузер
уходит обычной навигацией — забирать его через `fetch` означало бы держать
весь zip в памяти вкладки. Но у навигации нет способа показать ошибку:
ответ с текстом отказа просто заменил бы собой страницу, а правило 12.4
требует показать либо успех, либо причину отказа. Поэтому кнопка сначала
спрашивает разрешение (`?check=1` → JSON со сводкой), и лишь получив его,
переходит по ссылке. Тот же ответ сообщает `skipped` — сколько из
выбранного пользователю недоступно, чтобы неполный архив не приезжал молча.

**Имена внутри архива** приводятся к базовому (`os.path.basename`) и
разводятся по дубликатам (`договор (2).pdf`). Первое — потому что
`original_name` пришёл из браузера и может содержать `../../` (zip slip);
второе — потому что дедупликация делает одинаковые имена нормой, а два
одинаковых имени в zip оставили бы пользователю один файл вместо двух.
Уникальность проверяется по **полному** пути, а не по имени: два
`приказ.pdf` в разных папках — норма, и приписка «(2)» к одному из них
была бы враньём о его имени.

**Скачивание папки** — тот же механизм, отличается только тем, что у
записей есть путь. Каждый элемент архива это пара `(путь, FileObject)`, где
путь — кортеж названий папок; у массового скачивания выбранного он пустой
(файлы могли прийти из разных папок, и восстанавливать их вложенность никто
не просил), у папки — её дерево, начиная с неё самой, чтобы при распаковке
получилась папка, а не вывалившееся в корень содержимое.

Дерево собирает `storage.utils.folder_subtree()` — один обход на три модуля
вместо трёх копий `_subtree_ids`, которые до этого жили в каждом
`views.py`. Он же принимает `queryset`, ограничивающий видимые папки: у
приватного доступа `allowed_users` задаётся НА ПАПКЕ, поэтому вложенная
может быть закрыта при открытой родительской, и такая ветка обрывается
целиком — иначе архив стал бы способом выгрузить то, что в интерфейсе даже
не показывается.

У обменника папка верхнего уровня — сам сотрудник, а не запись
`ExchangeFolder`: у файлов в корне личной папки `folder=None`, и обычным
обходом дерева они недостижимы, поэтому личная папка скачивается отдельным
адресом (`exchange_personal_download`).

Пустые подпапки в архив не попадают: записи создаются только под файлы.
Для «скачать папку с содержимым» это то, что нужно, но если однажды
понадобится точный слепок структуры — добавлять записи-каталоги
(`ZipInfo` с завершающим `/`).

Права, как и везде, сужает модуль-потребитель: во вьюху приходят id в
query-строке, и без фильтра по правам архив выгрузил бы закрытые папки
`deptdocs` целиком. Общая половина (разбор `?ids=`, пределы, оформление
ответа) живёт в `storage.utils.fm_archive_view()` — по той же причине, что
и остальной раздел 12: три копии разошлись бы.

### 8.2. Загрузка архива с распаковкой

Обратная операция, и мотивация у неё не «удобно», а «иначе портал не
внедрить»: действующие документы организации лежат в расшаренных сетевых
папках, и переносить их через форму загрузки по одному никто не станет.
`storage/archives.py` разбирает загруженный zip, а папки и записи создаёт
модуль-потребитель — storage по-прежнему не знает ни `CatalogDocument`, ни
`allowed_users` (раздел 1). Потребитель передаёт две функции,
`ensure_folder(parent, name)` и `create_record(file_object, folder, name)`,
и задачу-обёртку держит у себя (`catalog.tasks.import_catalog_archive` и
соседи) — тот же приём, что и с очисткой корзины в 6.1.

**Кодировка имён — главная практическая проблема, а не мелочь.** В zip есть
флаг 0x800 «имена в UTF-8». Если он не выставлен, стандарт предписывает
cp437, и `zipfile` честно так и декодирует — а windows-архиваторы писали
русские имена в cp866. «Приказы» превращается в «╧ЁштъЁ√». Придут именно
такие архивы: их собирали на рабочих станциях из тех самых сетевых папок.
Поэтому имя без флага перекодируется обратно в байты по cp437 и читается
как cp866 (`decode_entry_name`); для ASCII преобразование тождественно.

**Архив от пользователя не доверенный.** До того, как на диск ляжет первый
байт, `inspect_archive()` читает только оглавление и отбивает: не-zip,
пустой, защищённый паролем (спросить пароль негде, а молча пропустить
записи — оставить пользователя с пустой папкой без объяснения), превышение
`STORAGE_ARCHIVE_MAX_FILES` / `STORAGE_ARCHIVE_MAX_TOTAL_SIZE` и
несоразмерное отношение сжатия (`STORAGE_ARCHIVE_MAX_RATIO` — zip-бомба
ловится по оглавлению, до чтения потока). Пути с `..` отбрасываются: имена
из архива становятся НАЗВАНИЯМИ ПАПОК модуля.

Размеру в оглавлении тоже нельзя верить — его заявляет тот, кто собрал
архив. Поэтому предел на отдельный файл проверяется по **фактически
прочитанным** байтам, а чтение обрывается на превышении. Расхождение с
заголовком ловит сам `zipfile` (не сходится CRC) — важно, что это не роняет
всю задачу: битая запись уходит в отчёт «пропущено», остальные файлы
доезжают.

**Каждый файл заводится через `StorageService.upload()`**, а не записью на
диск: иначе мимо пройдут дедупликация, квота и аудит. Дедупликация тут даёт
основную экономию — в сетевых папках один документ лежит в десятке копий, а
на портал ляжет одной. `upload()` и `create_record()` идут в одной
транзакции: иначе при сбое вставки остался бы `FileObject` в `ACTIVE` без
единой ссылки, то есть blob, живущий вечно (5.5).

**Сам архив попадает в storage как обычный файл** и отвязывается задачей по
завершении (в `finally`, иначе при падении он остался бы `ACTIVE` навсегда).
Не временный файл на диске: задачу выполняет другой процесс, и `blobs/` —
единственное место, где в этом проекте лежат файлы (раздел 3). Побочное
следствие: на архив действует общий `STORAGE_MAX_UPLOAD_SIZE`, то есть
переносить сетевую папку придётся частями по 100 МБ.

## 9. Ограничения размера и квоты

Исходная мотивация проекта — риск переполнения диска. Дедупликация и очистка
сирот помогают, но не защищают от одного пользователя, заливающего сотни
гигабайт уникального содержимого. Поэтому лимиты — часть первой версии:

Пределы задаёт **администратор портала в /admin/** — единственная запись
`StorageLimits` (размер файла, квота, сроки хранения, пределы архивов).
`settings.py` остаётся источником значений по умолчанию: пока записи нет,
действуют они.

```python
# settings.py — умолчания, пока запись не заведена
STORAGE_MAX_UPLOAD_SIZE = 100 * 1024 * 1024      # 100 МБ на один файл
STORAGE_USER_QUOTA = 2 * 1024 * 1024 * 1024       # 2 ГБ на пользователя, None = без квоты
STORAGE_ORPHAN_RETENTION_DAYS = 7                # сколько blob лежит в ORPHAN до удаления
```

Почему в БД, а не в `settings.py`: «100 МБ на файл» и «7 дней на вложение
чата» — вопрос эксплуатации, а не кода. Пока они лежали в настройках,
каждое изменение требовало разработчика и перезапуска Daphne.

Все обращения идут через `storage/limits.py`, и значение читается **при
каждом вызове**. Кеша намеренно нет: смысл настройки в админке — подействовать
сразу, а `LocMemCache` живёт в одном процессе из нескольких, и половина
воркеров ещё какое-то время работала бы по старому числу. Запрос идёт по
первичному ключу и на фоне самой загрузки файла незаметен.

Пустое поле квоты — это «без ограничения», а не «взять из settings»: иначе
снять квоту в админке было бы нечем.

Отказ обязан называть действующее число («Файл больше допустимых 7.0 МБ»,
«Не хватает места: квота 1.0 ГБ, занято 0.9 ГБ»). Пока предел лежал в
коде, «файл слишком большой» ещё можно было объяснить инструкцией; теперь
его правит администратор, и сообщение без числа не даёт пользователю
способа понять, во что он упёрся.

2 ГБ выбраны из профиля нагрузки: портал хранит офисные документы (приказы,
бланки, инструкции), а не медиатеку — это тысячи файлов на человека, с
запасом на переписку и обменник. Дедупликация уже гасит основной риск
(документ, разосланный всем сотрудникам, учитывается в квоте один раз —
`get_usage()` считает по уникальным blob'ам), квота ловит именно случай
одного пользователя, заливающего гигабайты уникального содержимого.
Значение меняется одной строкой без миграций и без переделки
модулей-потребителей — `QuotaExceededError` уже обработан во всех view
загрузки.

- `upload()` отклоняет файл больше предела размера
  (`FileTooLargeError`) **до** записи на диск.
- `get_usage(user)` возвращает сумму `blob.size` по **уникальным** blob'ам, на
  которые ссылаются `FileObject` пользователя, — иначе дедуплицированный файл
  учитывался бы многократно.
- Превышение квоты — `QuotaExceededError`, тоже до записи на диск.

## 10. API для потребителей

```python
from storage.services import StorageService
from storage.exceptions import FileTooLargeError, QuotaExceededError
from storage.models import FileObject
```

### Загрузка

```python
class UploadExchangeFileView(LoginRequiredMixin, View):
    def post(self, request, recipient_id):
        recipient = get_object_or_404(get_user_model(), pk=recipient_id)

        try:
            file_object = StorageService.upload(
                request.FILES['file'], user=request.user, category=FileObject.Category.EXCHANGE,
            )
        except FileTooLargeError:
            return JsonResponse({'error': 'Файл слишком большой'}, status=400)
        except QuotaExceededError:
            return JsonResponse({'error': 'Превышена квота хранилища'}, status=400)

        exchange_file = ExchangeFile.objects.create(
            file_object=file_object, owner=recipient, uploaded_by=request.user,
        )
        return JsonResponse({'id': exchange_file.id})
```

Никакого `attach()` — `upload()` уже вернул объект, чей blob в `ACTIVE`.

### Удаление в корзину и восстановление

```python
class TrashExchangeFileView(LoginRequiredMixin, View):
    def post(self, request, file_id):
        exchange_file = get_object_or_404(ExchangeFile, pk=file_id, owner=request.user, is_deleted=False)
        exchange_file.is_deleted = True
        exchange_file.deleted_at = timezone.now()
        exchange_file.deleted_by = request.user
        exchange_file.save(update_fields=['is_deleted', 'deleted_at', 'deleted_by'])
        # detach() НЕ вызывается — файл ещё можно восстановить
        return JsonResponse({'success': True})


class RestoreExchangeFileView(LoginRequiredMixin, View):
    def post(self, request, file_id):
        exchange_file = get_object_or_404(ExchangeFile, pk=file_id, owner=request.user, is_deleted=True)
        exchange_file.is_deleted = False
        exchange_file.deleted_at = None
        exchange_file.deleted_by = None
        exchange_file.save(update_fields=['is_deleted', 'deleted_at', 'deleted_by'])
        return JsonResponse({'success': True})
```

### Окончательное удаление

```python
def purge_exchange_file(exchange_file, *, user=None):
    file_object = exchange_file.file_object
    exchange_file.delete()
    StorageService.detach(file_object, user=user, consumer='exchange.ExchangeFile')
```

Порядок важен: сначала удаляется FK-запись потребителя, затем `detach()` —
иначе `_has_references()` увидит собственную, ещё не удалённую ссылку.

### Скачивание с проверкой прав

```python
class DownloadDepartmentDocumentView(LoginRequiredMixin, View):
    def get(self, request, doc_id):
        doc = get_object_or_404(DepartmentDocument, pk=doc_id, is_deleted=False)

        if not doc.allowed_departments.filter(pk=request.user.cat_id).exists():
            raise PermissionDenied

        return StorageService.get_download_response(doc.file_object, request)
```

### Чек-лист подключения нового потребителя

1. Модель с `ForeignKey('storage.FileObject', on_delete=models.PROTECT)` и
   полями корзины (`is_deleted`, `deleted_at`, `deleted_by`), если для неё
   нужна корзина.
2. View загрузки вызывает `StorageService.upload()` с правильной `category` и
   обрабатывает `FileTooLargeError` / `QuotaExceededError`.
3. Удаление — в корзину (флаг), окончательное — обычным `instance.delete()`;
   `detach()` выполнит сигнал (5.5). Перед удалением пометить инициатора
   через `attribute_deletion()`, иначе журнал не сохранит, кто удалил.
   **Тест обязателен**: «окончательное удаление объекта X переводит blob без
   других ссылок в ORPHAN» — см. `storage/tests/test_consumers.py`.
4. View скачивания проверяет права **до** вызова `get_download_response()` и
   не отдаёт объекты из корзины.
5. `queryset.delete()` и `bulk_delete` по моделям со ссылкой на `FileObject`
   применять с осторожностью: blob'ы они освободят корректно (сигнал
   `post_delete` рассылается и при массовом удалении), но пометку
   `attribute_deletion()` поставить некуда, поэтому в журнале удаление
   останется без инициатора. Где атрибуция важна — удалять записи по одной.
6. Категория добавлена в `FileObject.Category` и в `STORAGE_CATEGORY_TTL`.

Регистрировать модель где-либо не требуется — `_has_references()` находит её
через интроспекцию автоматически.

## 11. Миграция существующих файлов (выполнена)

Перевод существующих модулей на storage завершён. Мигрировали ровно две
модели — те, где файлы имеют смысл разделяемости с каталогом и обменником:

| Модель | Было | Стало | Категория |
|---|---|---|---|
| `posts.PostFile` | `file = FileField` | `file_object = FK(FileObject)` | `document` |
| `phonebook.Phonebook` | `book = FileField` | `file_object = FK(FileObject)` | `catalog` |

Остальные файловые поля остались на `FileField`/`ImageField` (см. 1.1).

**Данных не переносили.** Портал не в проде, БД Postgres поднималась с нуля,
таблицы `posts_postfile` и `phonebook_phonebook` были пусты — поэтому вместо
осторожной схемы «добавить поле → команда миграции с dry-run → переключить
код → удалить старое» сделана прямая замена поля одной миграцией схемы.
Команда `migrate_files_to_storage` не понадобилась и не писалась.

Что потребовалось помимо самой замены поля:

- `PostFile.original_name` / `size_display` / `extension` стали
  properties, проксирующими к `FileObject`/`FileBlob` — шаблоны, которые их
  используют, править не пришлось.
- Прямые ссылки `{{ f.file.url }}` в шаблонах заменены на view с проверкой
  прав (`post_file_download`, `phonebook_view_file`).
- `UpdateBookForm` сужена до `fields = ['title']`: `ModelForm` с FK на
  `FileObject` отрисовал бы выпадающий список файлов вместо
  `<input type=file>`. Файл обрабатывается вручную в `form_valid()`.
- В `PhoneBook.form_valid()` при замене файла старый `FileObject`
  отвязывается через `detach()` — иначе прежний blob остался бы `ACTIVE`
  навсегда.

**Побочная находка.** При тестировании удаления поста выяснилось, что
`PostDeleteView` переопределял `delete()`, который в Django ≥ 4.0 **не
вызывается на POST-запрос**: POST идёт через `post() → form_valid() →
object.delete()`. Переопределение было мёртвым кодом — посты удалялись, а
`detach()` не вызывался ни разу, и `FileObject` копились как `ACTIVE`
бесконечно. Исправлено переносом логики в `form_valid()`.

## 12. Интерфейсный слой файлового менеджера

Раздел описывает общий слой UI трёх модулей-потребителей (обменник,
каталог, приватный доступ). К хранению файлов он отношения не имеет и
живёт в `storage` по той же причине, что и `utils.apply_sort`: он нужен
всем трём одинаково, а дублировать его в каждом модуле — гарантированно
получить три разошедшиеся копии (так уже случилось с карточками файлов:
в одной был «Просмотр» для любых типов, в другой всё меню пряталось за
`can_upload`, в третьей не было пункта пересылки).

### 12.1. Живые обновления (WebSocket)

Файловый менеджер — совместное пространство: в одну папку одновременно
пишут несколько человек. Без живых обновлений сосед узнавал о новом файле
только вручную обновив страницу, а пользователь, работавший со списком,
видел неактуальное состояние и получал 404 при действии над уже удалённым
файлом.

- `storage/realtime.py` — группы и `broadcast()`. Группа заводится на
  **конкретную папку**, а не одна общая на портал: событие «Иванов
  переименовал файл» интересно только тем, кто смотрит именно эту папку.
  Важнее второе: у приватного доступа содержимое закрыто списком
  `allowed_users`, и общая группа означала бы рассылку имён файлов из
  закрытых папок всем подключённым.
- `storage/consumers.py` — `FileManagerConsumer`. Доступ проверяется
  **один раз при подключении**, по той же логике потребителя, что и в
  разделе 8. Для `deptdocs` — `folder.is_accessible_by(user)`.
- `broadcast()` **никогда не роняет операцию**: если брокер недоступен,
  ошибка уходит в лог, а файл остаётся загруженным. Обратное поведение
  означало бы 500 на успешно выполненном действии, а повтор создал бы
  дубликат. Тест — `test_fm_ui_layer.RealtimeBroadcastTest`.

Событие намеренно **не несёт содержимого изменения** — только «здесь что-то
поменялось» плюс имя инициатора для тоста. Получив его, клиент
перезапрашивает саму сетку (см. 12.2).

### 12.2. Частичный рендер сетки

`storage.utils.PartialGridMixin` учит `ListView` отдавать по `?partial=1`
только сетку карточек (`<module>/_grid.html`) вместо целой страницы.
Клиент подменяет ею кусок DOM — и при своём действии, и по событию из
12.1. `window.location.reload()` в файловом менеджере больше не
используется.

Почему перерисовывается серверный HTML, а не собирается карточка в JS:
карточка рендерится include-шаблоном, внутри которого проверки прав
(`{% if fm_can_manage %}`). Вторая реализация той же разметки и тех же
правил на JS обязана была бы совпадать с первой — и перестала бы
совпадать при первом же изменении правил. Лишний GET на событие дешевле
расхождения прав между серверным и клиентским рендером.

Из этого следует требование к `_grid.html`: **всё, что должно обновляться
живьём, лежит внутри него**, включая пагинацию — иначе после удаления
последнего файла страница предлагала бы несуществующие страницы.

### 12.3. Удаление папки

Удаление папки — единственное место, где каскад мог унести пользовательские
файлы мимо корзины (раздел 6). Флага `is_deleted` для этого недостаточно:
`folder` у всех трёх моделей-потребителей объявлен с `on_delete=CASCADE`,
и `folder.delete()` сносит записи независимо от их флагов. Поэтому
содержимое поддерева сначала **отвязывается от папки**, и лишь затем
удаляется сама папка:

| Модуль | Куда переезжает содержимое |
|---|---|
| `exchange` | `folder=None` — корень личной папки владельца |
| `catalog` | `folder=None` — корень каталога |
| `deptdocs` | родительская папка |

`deptdocs` — исключение, потому что там документ вне папки не наследует
ничьих прав и не виден никому (`DepartmentDocument`), то есть выпал бы и
из корзины, которая фильтруется по `folder__allowed_users`. У корневой
папки родителя нет, девать документы некуда — удаление такой папки с
документами **отклоняется** с объяснением. Тесты —
`storage/tests/test_folder_deletion.py`.

### 12.4. Правило про контролы

Панель фильтров, селектор размера страницы и чекбоксы на карточках папок
были перенесены из макета Midone как есть и не делали ничего. Контрол,
который выглядит рабочим и молча игнорируется, вводит в заблуждение
сильнее, чем его отсутствие, поэтому действует правило: **контрол либо
работает, либо его нет в разметке**. Отсюда:

- расширенный фильтр реализован (`storage.utils.apply_filters`);
- `?per_page=` реально управляет пагинацией, а селектор выводится только
  там, где вьюха это поддерживает;
- чекбокс на карточке папки не рисуется, если папка не участвует в
  выделении;
- пункт «Просмотр» показывается только для типов, которые браузер
  действительно умеет открыть (`fm_tags.is_previewable`).

Сюда же относится обратная связь: любое действие обязано либо показать
успех, либо показать причину отказа. Прежние обработчики проверяли только
`data.success` и не имели `.catch()` — при 403 сервер отдаёт HTML,
`r.json()` бросал исключение, и кнопка молча не срабатывала.

## 13. Конвертация офисных документов в PDF

Браузер рисует в `<iframe>` только PDF и картинки (см. `is_inline_safe`,
раздел 8). Половина справочников организации загружена в `.docx` и `.xlsx`,
то есть пользоваться ими на портале было нельзя: страница честно
показывала карточку «файл нужно открыть в офисном редакторе».

**Конвертирует внешний LibreOffice** (`storage/convert.py`,
`soffice --headless --convert-to pdf`), а не питоновская библиотека. Причина
простая: библиотеки, которая верстала бы `.docx` с приемлемым результатом,
нет — те, что есть, либо требуют установленного MS Word (значит, не работают
на Астре), либо пересобирают документ по-своему. LibreOffice на Астре стоит
по умолчанию, отдельной зависимости в проекте не появляется.

Решения, которые стоит помнить:

- **Запуск в Celery.** soffice думает секунды-десятки секунд; держать на
  этом HTTP-запрос — показывать пользователю зависшую страницу.
- **Исходник копируется во временный файл с расширением.** На диске blob
  называется контрольной суммой без расширения, а фильтр LibreOffice
  выбирает по расширению — без копии он отказывается работать с файлом,
  тип которого «не распознан».
- **Свой профиль (`-env:UserInstallation`) на каждый запуск.** С общим
  профилем второй soffice не запускается, а молча передаёт работу первому и
  завершается с кодом 0 — задача отчиталась бы об успехе, не создав PDF.
- **Код возврата — не показатель.** soffice отдаёт 0 и когда ничего не
  сконвертировал; признак успеха — появившийся файл.
- **PDF-копия лежит отдельным полем**, оригинал остаётся тем, что загрузили:
  кнопка «Скачать файл» отдаёт исходный документ, а не пересборку.
- **Результат сверяется с исходником.** Конвертация идёт секунды, за это
  время справочник могли заменить; без сверки `file_object` к новому файлу
  прикрепился бы PDF от старого, и сотрудник читал бы прошлогодний
  справочник, не зная об этом.
- **Нет LibreOffice — нет кнопки.** Путь задаётся `STORAGE_SOFFICE_PATH`
  (пусто — искать в PATH и обычных местах установки); если не найден,
  «Показать в браузере» не появляется вовсе (правило 12.4).

Сейчас конвертация подключена к справочникам (`phonebook`). Модуль
`storage/convert.py` от них не зависит — каталогу и документам отделов её
можно включить тем же способом.

## 14. На будущее

- **Антивирусная проверка** — точка расширения в `upload()`: сканирование
  (например, ClamAV через `clamd`) содержимого в `temp/` до создания
  `FileBlob`. Схему не меняет.
- **Версии файла** — `previous_version = FK('self', null=True)` на
  `FileObject` (не на `FileBlob` — версионируется именованный документ, а не
  содержимое). Схему удаления не меняет.
- **Celery** — при появлении в проекте команды из раздела 7 переносятся в
  periodic tasks один-в-один.
- **Перенос хранилища в S3/MinIO** — меняются только `DEFAULT_FILE_STORAGE` и
  реализация `get_download_response()` (pre-signed URL вместо
  `X-Accel-Redirect`). Модули-потребители не затрагиваются вообще — ради этого
  и вводился сервисный слой.
