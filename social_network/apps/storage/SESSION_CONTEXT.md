# Контекст для новых сессий — storage, файловые модули и профили

Служебный файл, не документация проекта. Цель — дать новой сессии Claude

## Что это за проект

Django 5.0.1 + Channels/Daphne (ASGI) внутренний портал организации
(«Сеть-УК»). Windows-разработка (`c:\Users\User\Desktop\social_network`),
прод предполагается на Astra Linux. Git user `DreemzDev`, ветка `main`.

Реальное окружение: PostgreSQL (`portal`/`postgres`/`123`@127.0.0.1:5432),
Redis для Channels и Celery (`db=1` для Celery, чтобы не смешивать с
WS-трафиком). Виртуальное окружение — `.venv` в корне репозитория (НЕ `venv`,
тот путь битый и упоминается только в устаревшем `start_server.bat`).

Способ запуска. **Redis нужен первым** — на нём и Channels (живые
обновления, чат), и Celery; без него страницы откроются, но живые
обновления и массовые операции работать не будут:

```powershell
# 1. Redis (установлен в C:\Redis, автозапуска нет)
Start-Process -FilePath "C:\Redis\redis-server.exe" -WindowStyle Hidden
```

```bash
# 2. Сам портал (ASGI — обязателен для WebSocket, runserver не подходит)
cd c:/Users/User/Desktop/social_network/social_network
../.venv/Scripts/daphne.exe -b 127.0.0.1 -p 8000 social_network.asgi:application

# 3. Воркер — для массовых операций и очистки корзины. Без него bulk-запрос
#    вернёт task_id, задача не выполнится, а фронт будет опрашивать PENDING
#    бесконечно.
../.venv/Scripts/celery.exe -A social_network worker --loglevel=info --pool=solo

# 4. Beat — только если нужны периодические задачи по расписанию
../.venv/Scripts/celery.exe -A social_network beat --loglevel=info
```

```powershell
# 5. nginx — только когда нужно проверить прод-путь отдачи файлов
#    (X-Accel-Redirect, запрет /media/storage/). В обычной разработке не
#    нужен: при DEBUG=True файл отдаёт сам Django.
$nginx = "C:\Users\User\Desktop\social_network\social_network\nginx-1.28.0"
& "$nginx\nginx.exe" -p $nginx -t          # проверить конфиг
Start-Process "$nginx\nginx.exe" -ArgumentList "-p","." -WorkingDirectory $nginx
& "$nginx\nginx.exe" -p $nginx -s stop     # остановить
```

Проверять прод-путь надо при `DEBUG=False`, иначе ветка с `X-Accel-Redirect`
просто не выполняется. Менять `settings.py` ради этого не нужно — достаточно
временного модуля рядом и переменных окружения:

```bash
# settings_prodcheck.py:  from social_network.settings import *  /  DEBUG = False
DJANGO_SETTINGS_MODULE=settings_prodcheck PYTHONPATH="<каталог с модулем>;." \
    ../.venv/Scripts/daphne.exe -b 127.0.0.1 -p 8000 social_network.asgi:application
```

Daphne **не перезагружается сам** — перезапускать надо и после правки
Python-кода, и после правки шаблонов. Раньше здесь было записано, что
шаблоны подхватываются сами; 17.08.2026 это проверено фактом и оказалось
неверным: правка `register.html` не появлялась в ответе сервера, пока
процесс не перезапустили, а после перезапуска появилась сразу. Проверялось
маркером в разметке и `curl`, при `DEBUG=True` (отладочная страница 404
подтверждает).

Статика перезапуска не требует — она читается с диска на каждый запрос.

## Модуль storage — единый сервис хранения файлов

Полное архитектурное обоснование — `apps/storage/ARCHITECTURE.md` (читать
его, если нужно понять «почему», не «что»). Коротко: `FileBlob` (физическое
содержимое, `checksum` unique, дедупликация) + `FileObject` (именованное
использование, на него ссылаются потребители). Права доступа — не в storage,
их проверяет каждый модуль-потребитель сам.

Ключевые баги, найденные аудитом и исправленные (тесты в `apps/storage/tests/`):

1. **`_object_has_references()` всегда возвращала `False`** — обходила
   `FileObject._meta.get_fields()`, но все потребители используют
   `related_name='+'`, который подавляет обратные связи. Исправлено на обход
   `apps.get_models()`. Тест: `test_references.py`.
2. **Прямой доступ к файлам в обход прав** — `/media/storage/blobs/<checksum>`
   раздавался как обычная медиатека. Закрыто перехватчиком `^media/storage/`
   в корневом `urls.py` (404 до `static()`). Тест: `test_direct_access.py`.
3. **Автоочистка по TTL не работала** — `purge_expired_objects()` в storage
   вызывала `detach()`, который защищал файлы с живыми ссылками, но функция
   отчитывалась об успехе, не удалив ничего. Убрана из storage; каждый
   потребитель, которому нужен TTL, пишет свою periodic task (см.
   `exchange.tasks.cleanup_expired_exchange_files`).
4. **Каскадное удаление обходило `detach()`** — чек-лист требовал ручного
   вызова `detach()`, но каскад от FK сносит запись потребителя сам, и
   вызвать его некому. Реальные пути: `CatalogFolder` → `CatalogDocument`,
   `DepartmentFolder` → `DepartmentDocument`, деревья папок через `parent`
   (включая `ExchangeFolder`, добавленную позже), `User` → `ExchangeFile`
   (`owner`). Blob оставался `ACTIVE` без ссылок навсегда. Исправлено
   сигналом `post_delete` в `storage/signals.py` — `detach()` выполняется
   автоматически для всех потребителей (интроспекция та же, что в 5.2).
   Атрибуция «кто удалил» передаётся пометкой `attribute_deletion()` перед
   `delete()`. Подробности — ARCHITECTURE.md, раздел 5.5. Тесты:
   `test_cascade.py`, `test_consumers.py`, `test_exchange_folders.py`.
5. **`StorageService.get_storage_stats()` падал с `NameError`** —
   использовал `models.Count()` без импорта `models` (был только
   `from django.db.models import Sum`). Ловилось только при заходе персонала
   (`is_staff`) на `/storage/` — обычные пользователи эту ветку не видели,
   баг был бы незаметен до первой жалобы. Исправлено импортом `Count`.
6. **`Content-Disposition` с кириллицей ломался на прод-пути.** Имя
   подставлялось в заголовок как есть, а `HttpResponse` кодирует значение
   вне latin-1 по RFC 2047 (`=?utf-8?b?…?=`) — форму, которой
   `Content-Disposition` не знает. Браузер сохранил бы файл под base64-строкой
   или под именем-хэшем из URL. Задевало почти каждое скачивание (имена в
   портале кириллические) и **только прод**: в ветке `DEBUG` заголовок
   собирает `FileResponse`, который сам оформляет имя по RFC 5987. Найдено
   при написании теста на `X-Accel-Redirect`, исправлено там же.
   Тест: `test_x_accel_redirect.py`.

Гонки на конкурентную загрузку/purge проверены на **реальном Postgres**
(`storage/tests/test_concurrency.py`) — на SQLite `select_for_update` и
`pg_advisory_xact_lock` не работают как надо, тесты были бы декоративными.

### Как запускать тесты — грабли

Приложения лежат в `apps/`, которая добавлена в `sys.path`, поэтому метка
теста — `storage`, а **не** `apps.storage` (с последней unittest падает в
discovery с `TypeError: path should be string... not NoneType`).

```bash
cd c:/Users/User/Desktop/social_network/social_network
../.venv/Scripts/python.exe manage.py test storage profiles --top-level-directory=apps
```

`.venv` лежит в корне репозитория, а `manage.py` — во вложенном
`social_network/`, поэтому из каталога с `manage.py` путь к интерпретатору
именно `../.venv/...`, а не `.venv/...`.

Меток теперь три: к `storage` и `profiles` добавилась `posts` (опросы).

Голый `manage.py test` без аргументов находит **0 тестов** — discovery
стартует из корня проекта и в `apps/` не заходит. Меток теперь **две**:
`apps/storage/tests/` (**323 штуки** на момент написания) и
`apps/profiles/tests/` (**32 штуки** — структура организации, см. раздел
«Структура организации» ниже). `tests.py` в остальных приложениях — пустые
заглушки Django. Тесты storage трогают
`exchange`/`catalog`/`deptdocs`/`profiles.Notification` напрямую, поэтому
метка `storage` тянет за собой их модели — так и задумано, отдельная
тестовая инфраструктура для каждого модуля не заводилась.

**Нужен поднятый Redis.** Часть тестов проходит через `notify()`, который
пушит событие в Channels, а тот идёт в Redis. Без него падает ~40 тестов
с `ConnectionError ... 6379`, и выглядит это как поломка кода, хотя дело
в окружении. Redis установлен в `C:\Redis`, поднимается так:

```powershell
Start-Process -FilePath "C:\Redis\redis-server.exe" -WindowStyle Hidden
```

Живые обновления файлового менеджера (`storage/realtime.py`) при упавшем
Redis, в отличие от `notify()`, ошибку не выбрасывают — пишут warning в
лог и продолжают (тест `test_fm_ui_layer.RealtimeBroadcastTest`).
`profiles.views._common.notify()` так не умеет — это старое поведение,
которое при падении Redis превращает успешное действие в 500; сюда стоит
вернуться отдельно.

**Тесты пишут медиа во временный каталог.** В `settings.py` под
`'test' in sys.argv` `MEDIA_ROOT` подменяется на `tempfile.mkdtemp()`.
Причина не косметическая: Django удаляет тестовую БД, но не файлы, и пока
каталог был общий с боевым, каждый прогон оставлял blob'ы в
`media/storage/blobs/` навсегда — накопилось 2887 файлов при 25 записях в
БД. Заодно это ломало дедупликацию **внутри** прогона: БД между тестами
откатывается, а файл остаётся, поэтому следующая загрузка того же
содержимого получала от `FileSystemStorage` имя с суффиксом
(`<checksum>_B24AkEu`).

Отсюда правило: **тест, который проверяет состояние диска, обязан брать
свой `MEDIA_ROOT` на каждый тест** (`override_settings` в `setUp`, см.
`test_deduplication.DeduplicationTest`). Общего каталога на прогон
недостаточно.

**`CELERY_TASK_ALWAYS_EAGER = 'test' in sys.argv`** в `settings.py` —
под `manage.py test` Celery-таски (`bulk_move_documents`,
`bulk_trash_documents`) выполняются синхронно в том же процессе, без
поднятого Redis/worker'а. Рядом же `CELERY_TASK_STORE_EAGER_RESULT` —
без него `AsyncResult(task_id).state` в eager-режиме не видит финальный
`SUCCESS` (Celery по умолчанию не пишет результат eager-задачи в backend).
Оба флага завязаны на один и тот же `'test' in sys.argv`, руками
переключать не нужно.

### exchange — важно про модель

Изначально был «файл адресован конкретному получателю» (как email-вложение),
потом переделан в открытую сетевую папку: папка = пользователь (нет
отдельной модели корневой папки), содержимое видно всем, удалять может
владелец папки или тот, кто загрузил.

**Подпапки (`ExchangeFolder`) добавлены позже, отдельным заходом.** Первая
версия ошибочно ограничивала создание/удаление подпапок только владельцем
личной папки — по аналогии с `deptdocs.DepartmentFolder`. Пользователь это
поправил: обменник открыт на запись всем, значит и подпапки должны быть
такими же — создать может кто угодно, удалить может владелец личной папки
или тот, кто создал подпапку (`ExchangeFolder.can_be_deleted_by`, тот же
принцип, что и у файлов). Если в коде/истории видите `can_be_managed_by`
или проверку `owner == request.user` на создание подпапки — это
промежуточное ошибочное состояние, актуальный метод —
`can_be_deleted_by`.

Владелец файла (`ExchangeFile.owner` — чья это личная папка) **меняется при
переносе** в папку другого сотрудника, см. раздел 8г ниже. Прежний запрет на
такой перенос снят; проверка вида `owner=exchange_file.owner` во вьюхе
перемещения — прежняя редакция.

### deptdocs — важно про модель

Документ сам не хранит прав — наследует их от `folder.allowed_users` (M2M
на конкретных людей, не отделы). Любой сотрудник может создать папку и
раздать доступ; любой участник равноправен с создателем, включая право
убрать самого себя (после чего мгновенно теряет видимость папки).

Найденный и исправленный баг: модалка «Доступ к папке» использовала ту же
переменную контекста `all_users`, что и модалка создания папки (там она
намеренно исключает текущего пользователя — «кому дать доступ, кроме
вас»). В модалке *редактирования* доступа существующей папки это давало
силовой баг: создатель не видел себя в списке чекбоксов, хотя реально
состоял в `allowed_users`, и при сохранении формы **терял себе доступ** —
его pk физически не мог попасть в отправленный список. Исправлено
разделением на `all_users_except_me` (создание) и `all_users` (просмотр
существующего доступа, полный список).

### phonebook — справочники организации

Справочник — документ, который сотрудник идёт читать: PDF показывается
прямо на странице в `<iframe>`, остальные форматы предлагаются к
скачиванию. Список справочников — подменю «Справочники» в главном меню
(контекст-процессор `phonebook.context_processors`, один лёгкий запрос на
страницу), последним пунктом «Добавить справочник» — она же страница
управления со списком и разделом удалённых.

Права намеренно не разделены: править может любой сотрудник, ответственность
держится на подписи, а не на запрете — так решил владелец портала.
Удаление мягкое (`storage.fmviews.TrashObjectView`), потому что иначе
увидеть, кто убрал справочник из меню, было бы негде.

Принимаются PDF, Word (DOC/DOCX/RTF), файлы Астра-офиса (ODT/ODS/ODP) и
таблицы с презентациями — список в `phonebook/forms.py`. **Показать в
`<iframe>` можно только PDF**: белый список inline-типов
(`storage.utils.is_inline_safe`) трогать нельзя, через него уже была XSS.
Для остальных форматов страница честно предлагает скачивание —
конвертация в PDF через LibreOffice запланирована следующим заходом
(см. «Куда развивать дальше»).

Дыра, закрытая здесь же: `/phonebook/<id>/` и `/phonebook/<id>/view/`
отвечали 200 без входа — коммит `b85b13e5` закрывал портал от анонимов и
эти два адреса пропустил. Вьюха принимала ещё и POST, то есть аноним мог
переименовать общий документ. Стережёт `AnonymousAccessTest`.

## Карта сети (`netmap`) — инвентарь адресов

Страница `/netmap/` **только для `is_staff`**: адреса, имена машин, кто за
что отвечает — служебная информация, и пункт меню обычному сотруднику не
показывается вовсе.

Устроено вокруг адреса, а не устройства: адреса в организации статические,
DHCP-аренд нет. Записи заводятся только тем адресам, что ответили;
свободные считаются как разница с диапазоном подсети — иначе на каждую /24
в БД лежало бы 254 пустые строки.

**Что даёт опрос** (`netmap/scanner.py`, только стандартная библиотека):
ping с разбором TTL, обратный DNS, ARP-таблица, короткая проба портов
(22, 445, 3389, 631, 9100, 80). По портам и TTL определяется ОС — это же
работает счётчиком перехода с Windows на Астру.

**Три вещи, которые надо знать, прежде чем что-то менять:**

1. **«Не отвечает» не значит «выключено».** Windows штатно режет ICMP
   файрволом. Поэтому хранится не флаг «онлайн», а метки времени и поле
   `reply_method` — чем именно ответил адрес: `ping`, `tcp` или `arp`.
   Оговорка про это выведена прямо на страницу, убирать её нельзя.
2. **Обход не затирает ручное.** Ответственный, кабинет, название и тип
   переживают ночной обход — на это есть тест
   (`test_manual_fields_survive_the_scan`). Данные обхода, наоборот, не
   редактируются: их перезапишет следующий обход.
3. **MAC заполняется только для своей подсети сервера.** За маршрутизатором
   его не видно в принципе, пустой MAC у дальних подсетей — норма.

Обход идёт задачей Celery потоками и **докладывает `PROGRESS`** — без этого
`FM.pollTask` через 20 секунд объявил бы задачу непринятой. Расписание —
через `django_celery_beat` в админке, задача `netmap.tasks.scan_all_subnets`.
Для ручного запуска есть `manage.py scan_network 10.10.0.0/24`.

**Решено не делать: LDAP к домен-контроллеру.** Обсуждалось как шаг 4 и
владельцем портала отменено. Вместе с ним отпала сверка «адрес отвечает, но
компьютера с таким именем в домене нет». Не заводить обратно без просьбы.

**Не проверено на живой сети.** Машина разработки в 10.10.0.0/24 не входит;
сканер проверен целиком на петле `127.0.0.0/30`. Первый настоящий обход —
за владельцем, он же покажет, режет ли их файрвол ICMP.

## Общий поиск по порталу

Поле в шапке (`/search/`, `profiles/views/search.py`). Выпадающий список и
страница результатов рисуются **одним шаблоном** — разметку отдаёт сервер,
JS её только подставляет.

**Права проверяет каждый модуль сам**, в своём `search.py`
(`exchange/`, `catalog/`, `deptdocs/`, `phonebook/`, `posts/`, `netmap/`).
Это не формальность: поиск ходит в модули напрямую, минуя их вьюхи. Без
проверки он показывал бы названия документов отдела тем, кому папка
недоступна, — утечка через заголовки тоже утечка. Стерегут тесты в
`profiles/tests/test_global_search.py`.

Добавляя модуль с содержимым, которое стоит искать, — заводить в нём
`search.py` с функцией `search(query, user, limit)` и дописывать строку в
`profiles/search.py`. Реестра с саморегистрацией нет намеренно: групп
шесть, явный список читается лучше.

## Пределы хранилища правятся в админке

`StorageLimits` — одна запись на портал (`/admin/`, «Пределы файлового
хранилища»): размер файла, квота сотрудника, сроки хранения корзины, сирот,
вложений чата и обменника, пределы архивов. `settings.py` остался
источником умолчаний: пока записи нет, действуют они, и на этом стоит вся
остальная сотня тестов.

Все обращения — через `storage/limits.py`, значение читается при каждом
вызове. Кеша нет намеренно: смысл настройки в админке — подействовать
сразу, а `LocMemCache` живёт в одном процессе из нескольких.

Числа видны там, где в них упираются: модалка загрузки архива называет
пределы, а отказ называет действующее значение («Файл больше допустимых
7.0 МБ»). Обоснование — ARCHITECTURE, раздел 9.

## Справочники Word и Excel открываются в браузере

`storage/convert.py` + `phonebook/tasks.py`: LibreOffice
(`soffice --headless --convert-to pdf`) в задаче Celery делает PDF-копию,
страница показывает её в `<iframe>`. Оригинал не подменяется — «Скачать
файл» отдаёт загруженный документ.

Что важно помнить (подробности — ARCHITECTURE, раздел 13): свой профиль
LibreOffice на каждый запуск, копия исходника с расширением, код возврата
soffice не показатель, результат сверяется с тем файлом, для которого
делался. **Нет LibreOffice — нет кнопки** «Показать в браузере».

Путь задаётся `STORAGE_SOFFICE_PATH` (пусто — искать самому). На машине
разработки LibreOffice **не установлен**: цепочка проверена живьём с
заглушкой вместо soffice, сам вызов LibreOffice на этой машине не
выполнялся ни разу.

## Файлы и фото в личной переписке

`profiles.MessageAttachment` поверх django_private_chat2 (её собственный
`MessageModel.file` не используется — обычный `FileField` в общей
медиатеке). Отправка — тем же HTTP-эндпоинтом, что и ответы на сообщения
(`send_message_reply`): через WebSocket библиотеки файл не передать.

- доступ — только двоим участникам диалога, проверяет `ChatAttachmentView`;
- срок хранения — из админки, по умолчанию 7 дней
  (`profiles/tasks.cleanup_expired_chat_attachments`, ставится в расписание
  через django_celery_beat, как остальные периодические задачи);
- по истечении срока запись остаётся, файл уходит: в пузыре появляется
  «файл удалён — вложения хранятся N дн.»;
- файлы принимаются **до** создания сообщения, иначе отказ на третьем файле
  оставил бы пузырь с частью вложений;
- удаление своего сообщения освобождает файлы сразу: `MessageModel` мягко
  удаляемая, каскада нет.

Грабля, стоившая времени: `ExtendedChatConsumer` собирает событие для
получателя **поле за полем**. Новое поле в `push_chat_event` надо
добавлять и туда — иначе у собеседника его просто нет, а серверные тесты
зелёные.

## Опрос в записи

`posts.Poll` / `PollOption` / `PollVote`. Вопрос — текст самой записи,
отдельного поля нет намеренно. Вариантов от 2 до 10, при желании с
несколькими ответами.

Голос один на человека: повторный клик по своему варианту снимает его,
клик по другому — переносит; уникальность пары «вариант — сотрудник»
держится на уровне БД. Итоги считаются в Python по
`prefetch_related('poll__options__votes')` — запрос на карточку в ленте из
десятков записей был бы тем самым N+1 (стережёт тест).

После голоса блок опроса приходит с сервера тем же шаблоном
(`includes/posts/poll.html`), которым рисуется при загрузке страницы:
второй реализации разметки на JS нет — тот же приём, что в файловом
менеджере.

В правке записи опрос можно только удалить: менять варианты, за которые
уже проголосовали, значит переписывать чужие ответы.

## Функционал файлового менеджера — что и зачем

Всё перечисленное ниже уже в `main`. Раздел нужен не как список задач, а
как карта: по каким ключевым словам искать нужное место и какое решение
за каждым пунктом стоит.

### 1. Подпапки обменника (`ExchangeFolder`)
Модель + миграция `0003_exchangefolder_exchangefile_folder.py`. Права —
см. раздел выше.

### 2. Единая страница корзины с табами
`/storage/trash/` (`storage.views.UnifiedTrashView`, шаблон
`templates/storage/trash.html`) — раньше у каждого модуля была отдельная
корзина по своему адресу, визуально неотличимая от других (тот же layout,
тот же заголовок «Корзина»). Легко было открыть не ту и решить, что файл
пропал. Новая страница собирает все три queryset'а (с теми же правилами
видимости, что и в отдельных `TrashView`) на одной странице, табы Alpine.
Старые адреса (`exchange_trash`, `catalog_trash`, `deptdocs_trash`) не
удалены, работают как есть — `fm_menu.html` теперь ссылается на
`storage_trash`.

### 3. Dashboard занятого места
`/storage/` (`StorageDashboardView`) — своя квота с прогресс-баром,
сводка по всему хранилищу для персонала (`get_storage_stats()`, см. баг
№5 выше), кнопка «Очистить сейчас» для каждой корзины.

### 4. Автоочистка корзины по сроку (catalog, deptdocs)
Раньше была только у обменника (TTL от даты загрузки, случайно захватывает
и корзину). У каталога и приватного доступа автоочистки корзины не было
вообще — удалённое лежало там неограниченно. Добавлены
`catalog.tasks.cleanup_catalog_trash` / `deptdocs.tasks.cleanup_deptdocs_trash`,
`STORAGE_TRASH_RETENTION_DAYS = 30`, periodic tasks заведены дата-миграциями
по образцу `storage/migrations/0002_seed_periodic_tasks.py`.

### 5. Переименование, перемещение, копирование/пересылка
Rename и move — для файлов и папок во всех трёх модулях, с защитой от
циклов в дереве (`_is_descendant`) и проверкой прав/принадлежности папки.
Пересылка между разделами — `StorageService.copy_reference()`: новый
`FileObject` на **тот же** blob, без повторной записи на диск (не
`upload()` — там дедупликация уже не нужна, содержимое и так на месте).
Проверяет квоту получателя по `blob.size`, но не задваивает её, если
получатель уже "владеет" этим blob'ом.

### 6. Массовые операции — асинхронно через Celery
Bulk move/trash во всех трёх модулях уходят в `storage.tasks.bulk_move_documents`
/ `bulk_trash_documents` — батчами по 200, с `update_state(state='PROGRESS', ...)`.
Вьюхи возвращают `{'task_id': ...}` вместо готового результата. Опрос —
`/storage/task-status/<task_id>/` (`TaskStatusView`), общий для всех
модулей, polling с фронта (`fm-actions.js: fmPollTaskStatus`).

Право на удаление/перенос там, где оно не сводится к простому dict-фильтру
(`Q(owner=X) | Q(uploaded_by=X)` в обменнике), проверяется **во вьюхе до**
постановки задачи — задаче передаётся уже урезанный список id, сама задача
никаких прав не проверяет.

### 7. Уведомления о новых файлах
`profiles.Notification` получил `Kind.FILE_SHARED` и новое поле `url`
(миграция `0016_notification_url_alter_notification_kind.py`) — готовая
ссылка вместо FK на конкретный объект, потому что файл может быть в любом
из трёх модулей. `notify()` в `profiles/views/_common.py` принимает
`url=''`. Обменник уведомляет владельца папки при загрузке чужим
человеком (не себя), приватный доступ — всех участников `allowed_users`
кроме загрузившего. Каталог никого не уведомляет — общедоступен, рассылка
всем при каждой загрузке была бы шумом.

Живой JS в `base.html` (`prependNotificationItem`) раньше игнорировал
`url` в приходящем по WebSocket уведомлении — клик по свежему
уведомлению никуда не вёл, хотя статический список (`notification_center_items`)
уже поддерживал ссылки. Исправлено.

### 8. Сортировка и превью
`storage/utils.py: apply_sort()` — общий хелпер для `?sort=name/-name/
uploaded_at/-uploaded_at/size/-size`, недопустимые значения падают на
дефолт (`-uploaded_at`), не долетая до `order_by()` напрямую. Сортировка
по размеру идёт через `file_object__blob__size` — `FileObject.size` это
python-property, ORDER BY по нему на уровне SQL невозможен.

Превью в браузере — `?inline=1` на всех трёх download-эндпоинтах,
использует уже существовавший `StorageService.get_download_response(inline=True)`
(раньше применялся только для `phonebook`).

### 8а. Массовое скачивание одним zip
Кнопка «Скачать архивом» в панели выделения всех трёх модулей →
`*_bulk_download` → общая половина `storage.utils.fm_archive_view()` →
`StorageService.get_archive_response()`. Полное обоснование —
ARCHITECTURE.md, раздел 8.1; коротко, что важно помнить:

- архив собирается **на лету**, память не растёт с его размером;
- у буфера намеренно нет `seek()` — по этому признаку `zipfile`
  переключается на data descriptor и позволяет писать в поток. Добавите
  `seek()` — архивы станут битыми, поймает
  `test_bulk_download.test_archive_is_readable_although_built_on_an_unseekable_stream`;
- это **единственное** место, где содержимое идёт через воркер Daphne, а не
  через nginx, поэтому есть пределы `STORAGE_ZIP_MAX_FILES` (200) и
  `STORAGE_ZIP_MAX_TOTAL_SIZE` (1 ГБ);
- у адреса два режима: `?check=1` отдаёт JSON-сводку, без него — сам архив.
  Кнопка обязана сначала спросить: за архивом браузер уходит навигацией, и
  показать причину отказа в этот момент уже нечем.

Проверено не только тестами: через Daphne архив приезжает с
`Transfer-Encoding: chunked`, `testzip()` чист, data descriptor выставлен на
каждой записи, UTF-8 флаг — ровно на кириллических именах.

### 8б. Загрузка архива с распаковкой на сайте
Кнопка «Загрузить архив» в панели всех трёх модулей → `*_upload_archive` →
`storage.archives` + задача-обёртка у потребителя
(`catalog.tasks.import_catalog_archive` и соседи). Полное обоснование —
ARCHITECTURE.md, раздел 8.2. Что важно помнить:

- **Имена в cp866** — главная грабля. Без флага 0x800 `zipfile` декодирует
  имя как cp437, а windows-архиваторы писали cp866, и «Приказы» приезжает
  как «╧ЁштъЁ√». Придут именно такие архивы. Правит `decode_entry_name()`.
- Архив проверяется **синхронно во вьюхе** (только оглавление, это дёшево),
  поэтому «это не zip» и «архив под паролем» пользователь видит сразу, а не
  через опрос статуса задачи.
- Сам архив кладётся в storage обычным `upload()` и отвязывается задачей в
  `finally`. Отсюда следствие: архив ограничен `STORAGE_MAX_UPLOAD_SIZE`
  (100 МБ), большую сетевую папку надо переносить частями.
- Папки создаются `get_or_create`, поэтому повторная загрузка **доливает**
  файлы в существующие папки, а не плодит вторую «Приказы» рядом.
- У `deptdocs` подпапка наследует `allowed_users` от родителя. Папка с
  пустым списком не видна никому, включая создателя, — распакованное в неё
  просто исчезло бы из интерфейса.
- Битая запись не роняет импорт: уходит в отчёт «пропущено N» с причинами,
  остальные файлы доезжают.

Проверено на живом стенде архивом, собранным «как windows-архиватор»
(имена cp866 без флага): дерево `Приказы/2024/...` воссоздано, кириллица
читается, запись с `../` и `__MACOSX` пропущены, одинаковое содержимое
легло одним blob'ом, архив после импорта не остался ни в каталоге, ни в
`ACTIVE`.

### 8в. Скачивание папки целиком архивом
Пункт «Скачать архивом» в меню карточки папки во всех трёх модулях, плюс на
карточке сотрудника в списке папок обменника. Обоснование — ARCHITECTURE.md,
раздел 8.1. Что стоит помнить:

- элемент архива теперь пара `(путь, FileObject)`; у массового скачивания
  выбранного путь пустой, у папки — её дерево, начиная с неё самой;
- дерево собирает общий `storage.utils.folder_subtree()`. Он заменил **три
  копии** `_subtree_ids`, которые жили в `views.py` каждого модуля, — если
  понадобится обход поддерева, брать его, а не писать четвёртую;
- у приватного доступа обход идёт с `queryset` по `allowed_users`: закрытая
  подпапка обрывает ветку целиком, а не пропускается с сохранением потомков;
- у обменника личная папка сотрудника — **отдельный адрес**
  (`exchange_personal_download`): файлы в её корне имеют `folder=None` и
  обходом дерева недостижимы;
- одинаковые имена разводятся только внутри одной папки. Два `приказ.pdf` в
  разных каталогах — норма, приписка «(2)» была бы враньём;
- пустые подпапки в архив не попадают: записи создаются только под файлы.

Проверено живьём на демо-каталоге: `Инструкции.zip` приезжает потоком
(`Transfer-Encoding: chunked`), `testzip()` чист, внутри
`Инструкции/1111/file.pdf` — то есть дерево сохранено.

### 8г. Перенос между личными папками обменника
Пункт «Переместить» у файла и у папки обменника теперь предлагает личные
папки **всех сотрудников**, а не только подпапки текущей. Обоснование —
ARCHITECTURE.md, раздел 2, «Перенос между личными папками = смена
владельца». Что важно помнить:

- запрет был **осознанным решением с записанной причиной**, а не
  недоделкой; снят решением владельца портала — если увидите в истории
  докстринг «менять owner здесь не предполагается», это прежняя редакция;
- перенос в чужую папку меняет `owner`, а не только `folder`. Иначе файл
  пропал бы из интерфейса: список фильтруется по обоим полям сразу;
- вместе с владельцем уходит право удаления (`can_be_deleted_by`).
  Загрузивший его сохраняет — он и вернёт файл, если ошибся папкой;
- перенос подпапки меняет владельца **всего поддерева**, включая файлы в
  корзине: у них `folder` сохранён, и восстановление вернёт файл в
  переехавшую папку;
- назначение задаётся парой `owner_id` + `folder_id`; корень личной папки —
  это сам сотрудник, а не `ExchangeFolder`, и одним id не называется.
  В селекте своя подпапка — голый id, чужая — `owner:folder`, и двоеточие
  же служит признаком «папка чужая» для предупреждения в модалке;
- массовый перенос ходит через `storage.tasks.bulk_move_documents` с новым
  аргументом `extra_updates`: владелец и папка меняются **одним** update(),
  иначе между двумя запросами файл не виден ни там, ни там.

Проверено не только тестами: через живой Daphne с Celery — файл уходит в
корень чужой папки и пропадает из своей, массовый перенос возвращает его
обратно, у получателя появляется уведомление со ссылкой на его папку;
перенос подпапки с вложенной подпапкой и файлом внутри отдал получателю всё
поддерево, и вложенная папка у него открывается.

### 9. Общий JS-модуль `static/js/fm-actions.js`
Один файл на все три модуля вместо копии одного и того же кода в каждом
шаблоне. Публичный API — объект `window.FM`:

| Метод | Назначение |
|---|---|
| `FM.init(config)` | точка входа: выделение, массовые кнопки, drag&drop, WebSocket |
| `FM.action(url, data, opts)` | POST + тост + обновление сетки; единственный правильный способ дёрнуть эндпоинт |
| `FM.refresh()` / `FM.navigate(url)` | перерисовать сетку / перейти по странице без reload |
| `FM.confirm({...})` | модалка подтверждения вместо `confirm()` |
| `FM.toast(text, type)` | тост темы Midone (`$.toast` из её бандла) |
| `FM.upload(url, formData, opts)` | XHR — только он даёт `upload.onprogress` |
| `FM.pollTask(id, opts)` | опрос статуса Celery-задачи |

Действия карточек объявляются **декларативно на самой кнопке**
(`data-fm-action`, `data-fm-url`, `data-fm-confirm`, `data-fm-success`,
`data-fm-remove-card`) и обрабатываются одним делегатом на `document` —
поэтому те же кнопки работают и на страницах корзины, где сетки нет.
Подключается через `{% block extra_js %}` только на файловых страницах.

### Известные упрощения, не доведённые до конца
- У массового скачивания zip нет прогресса: `Content-Length` неизвестен
  (архив ещё не собран), поэтому браузер показывает скачивание без
  процента. Цена того, что первый байт уходит сразу.
- Сам JS (`fm-actions.js`) юнит-тестами не покрыт: проверяется серверная
  часть, от которой он зависит (рендер страниц, `?partial=1`, эндпоинты),
  но не поведение в браузере — JS-раннера в проекте нет.
- Перетаскивание работает на загрузку в текущую папку; перетаскивания
  карточки в папку (move drag&drop) нет.
- Папки не участвуют в массовых операциях (чекбокса у них нет намеренно):
  bulk-задачи работают над одной моделью, а папка — поддерево, и «удалить
  выбранное» означало бы разную семантику для разных элементов выделения.
  Перенос и удаление папки — поштучно, через её меню.
- У корзины массового восстановления/очистки нет, только поштучно.

### Перенос папок
Пункт «Переместить» есть у карточки папки во всех трёх модулях. У каталога
и приватного доступа эндпоинты (`*_folder_move`) существовали изначально,

(`MoveExchangeFolderView`).

Модалка переноса одна на файлы и папки, поэтому `moveTarget` — всегда
объект `{type, id}` (у папки свой эндпоинт и своё имя поля: `parent_id`,
новый родитель в дереве, а не папка-контейнер). Массовый перенос
использует ту же модалку со значением `moveTarget = 'bulk'`.

### Что было исправлено попутно
- **Утечка в приватном доступе**: список вложенных подпапок не
  фильтровался по доступу — были видны названия закрытых папок. На
  корневом уровне фильтр был, на вложенном нет.
- **Удаление папки шло мимо корзины** во всех трёх модулях (см.
  ARCHITECTURE.md 12.3). У каталога и приватного доступа удаления папок из
  UI вообще не было.
- **`copy_reference()` без блокировки blob'а** — гонка с `detach()`
  оставляла живую ссылку на blob в статусе ORPHAN.
- **Настройки storage читались при импорте модуля** — `override_settings`
  не работал, квота требовала рестарта.
- **`TaskStatusView` падал с TypeError** на задачах, возвращающих число
  (очистка корзины возвращает int, а не dict) — проявилось, когда очистку
  перевели с синхронного вызова на `.delay()`.
- **Мультизагрузка обрывалась на первой ошибке**, отвечая 400, хотя часть

- Мёртвые контролы (расширенный фильтр, селектор размера страницы,
  чекбоксы папок, «Настройки», метки в меню) — либо сделаны рабочими,
  либо убраны. Действует правило: **контрол либо работает, либо его нет в

- **Пагинация вставала сбоку от файлов**: она лежала внутри
  grid-контейнера и потому становилась такой же ячейкой сетки, как
  карточка. Сетка карточек и пагинация разведены в соседние блоки —
  если правите `_grid.html`, не заворачивайте пагинацию обратно внутрь
  `grid grid-cols-12`.

### Осталось незакрытым (важно)

Из дефектов кода — ничего. Пять пунктов, стоявших здесь раньше (устойчивость
`notify()` к падению Redis, доверие MIME-типу в `?inline=1`, отсутствие
проверки владения в `TaskStatusView`, 400 от Daphne на действиях без данных,
невидимые тосты), закрыты — см. «Дефекты, закрытые отдельным заходом» ниже.

Остаётся прод-конфигурация Django, но она сознательно отложена: портал ещё
в разработке. Перед разворачиванием — `DEBUG = False` (сейчас жёстко `True`
в `settings.py`, и именно по нему `get_download_response()` выбирает ветку
с `X-Accel-Redirect`), `SECRET_KEY` и пароль БД из окружения, а не из файла
(рядом лежат закомментированные `env(...)`), TLS (`CSRF_TRUSTED_ORIGINS`
уже содержит `https://`, а nginx слушает только 80) и реальный путь вместо
`/srv/portal` в `deploy/nginx/portal.conf`.

### Дефекты, закрытые отдельным заходом

1. **`notify()` роняла успешное действие при упавшем Redis.**
   `push_chat_event()` звал `group_send` без обработки ошибок: запись
   `Notification` уже в БД, файл уже загружен, а пользователь получал 500 и
   повторял загрузку, создавая дубликат. Теперь `try/except` + warning в лог,
   ровно как в `storage/realtime.py: broadcast()`. Исправлено в
   `push_chat_event()`, а не в `notify()`, потому что все семь вызывающих
   мест (чат, реакции, правки, удаления) устроены одинаково: доставка
   «живьём» — не часть операции. Тесты — `test_upload_notifications.NotifyBrokerFailureTest`.
2. **`?inline=1` доверял MIME-типу из аплоада** — загруженный `.html`
   открывался страницей в домене портала, то есть обычная загрузка файла в
   обменник давала хранимую XSS. Появился белый список
   (`storage/utils.py: is_inline_safe()`): `application/pdf`, `text/plain`,
   `text/csv`, `text/markdown` плюс префиксы `image/`, `video/`, `audio/`;
   `image/svg+xml` исключён отдельной строкой — SVG подходит под `image/`,
   но внутри него работает `<script>`. Небезопасный тип не отвергается, а
   **понижается до вложения**: пункта «Просмотр» для таких файлов в меню
   нет, значит сюда попадает только ссылка, собранная руками, и скачать
   файл — ровно то, что должно по ней произойти. `SVG` заодно убран из
   `PREVIEWABLE_EXTENSIONS`. `X-Content-Type-Options: nosniff` теперь ставит
   и Django (обе ветки), а не только nginx. Тесты —
   `test_inline_preview.InlineMimeWhitelistTest` и `IsInlineSafeTest`.
3. **`TaskStatusView` не проверял владения задачей.** Теперь запустивший
   запоминается в своей сессии, чужой `task_id` — 404.
   Сессия, а не кеш: `CACHES` в проекте не сконфигурирован, то есть это
   `LocMemCache` — память одного процесса. Чтобы запись нельзя было забыть,
   ответ и запоминание сведены в один хелпер `utils.fm_task_response(request, task)` —
   все семь мест запуска в четырёх модулях зовут его. Тесты — `test_task_status.py`.

   Попутно в `fm-actions.js`: `FM.pollTask` разбирал ответ, не глядя на HTTP-код,
   и на 404/403 уходил в ветку «неизвестное состояние», опрашивая сервер
   бесконечно. Там же появился предел ожидания состояния `PENDING` (20 с) —
   при незапущенном воркере опрос крутился вечно, показывая «Перемещение…»,
   то есть действие молча не работало вопреки правилу 12.4.
4. **Ни одно действие без данных не работало в браузере — 400 от Daphne.**
   Пожаловался пользователь: «не могу удалить файл даже в своей папке и не
   могу очистить корзину». `FM.post` собирал тело запроса через
   `new FormData()`, и для действий без параметров (в корзину,
   восстановить, удалить окончательно, удалить папку, переслать в каталог)
   получалось **multipart-тело без единой части**. Daphne отвечает на такое
   `400` ещё до Django: запроса нет даже в её access-логе, тело ответа
   пустое.

   Почему не поймали раньше: тестовый клиент Django кодирует пустой словарь
   как `x-www-form-urlencoded` и до Daphne не доходит вовсе, а `runserver`
   (WSGI) такой запрос спокойно пропускает — расхождение видно **только**
   на боевом сервере. Серверные тесты на удаление при этом были зелёные и
   остаются зелёными: вьюхи всегда работали правильно.

   Исправлено одной строкой: CSRF-токен теперь уходит и полем формы, и
   заголовком, поэтому тело никогда не бывает пустым (заодно запрос
   переживёт прокси, вырезающий нестандартные заголовки).
5. **Тосты не показывались вообще.** Midone кладёт стили
   jquery-toast-plugin в `app.css`, но сам плагин прячет внутрь своего
   бандла и вешает на jQuery, которую держит webpack. У подключённой
   отдельным файлом jQuery метода `.toast()` нет, и `FM.toast` тихо уходил
   в `console.log` — то есть **ни успех, ни причина отказа пользователю не
   показывались**, вопреки правилу 12.4. Из-за этого дефект №4 и выглядел
   как «кнопка ничего не делает». Теперь при отсутствии плагина `FM.toast`
   собирает ту же разметку (`.jq-toast-wrap` / `.jq-toast-single`) руками —
   оформление берётся из того же `app.css`, второй визуальной системы не
   появляется.

   Оба дефекта закрыты сторожем в `test_fm_ui_layer.FmActionsSourceTest`:
   он читает исходник `fm-actions.js`. Проверка грубая, но JS-раннера в
   проекте нет, а серверными тестами это не ловится в принципе — тот же
   приём, что с разбором конфигов nginx в `test_x_accel_redirect.py`.

   **Как проверять такое впредь:** Node в системе есть, Chrome тоже, и
   Chrome умеет CDP — headless-браузер поднимается за минуту и показывает
   и консольные ошибки, и коды ответов. Именно так этот дефект и был
   найден: серверный запрос из Python отвечал 200, а браузер получал 400.
6. **Починка дефекта №4 до пользователя не доехала — кеш статики.**
   Прямое продолжение предыдущего пункта, и урок отдельный. Пользователь
   вернулся с тем же «корзина не работает» и спросил, не в перезапуске ли
   сервера дело. Сервер был ни при чём: он отдавал уже исправленный
   `fm-actions.js`, а Chrome продолжал выполнять прежний **из своего
   кеша**. В ответе статики есть только `Last-Modified` — ни `ETag`, ни
   `Cache-Control`, — а такому ответу браузер назначает срок годности сам,
   примерно как 10% от возраста файла: скрипт, пролежавший без правок
   неделю, кешируется на часы. Замер через CDP: повторный заход на
   страницу давал `transferSize: 0`, то есть сервер не спрашивали вовсе.

   Лечилось бы `Ctrl+F5`, но знать о нём сотрудникам неоткуда, а
   касается это любой будущей правки JS и CSS. Поэтому `{% static %}`
   теперь дописывает к адресу время правки файла
   (`social_network/staticfiles.py`): правка меняет адрес — браузер обязан
   скачать заново; файл не менялся — адрес прежний, и кеш работает как
   задумано. `ManifestStaticFilesStorage` не подошёл: он требует
   `collectstatic`, а `STATIC_ROOT` здесь — он же каталог исходной статики.

   **Общий урок:** «сервер отдаёт правильное» и «пользователь получает
   правильное» — разные утверждения, и второе проверяется только в
   браузере с включённым кешем. Сторож —
   `test_fm_ui_layer.StaticVersioningTest`.

### nginx — закрыто

Прод-конфигурация приведена в порядок. Канонический конфиг лежит **в git**:
`social_network/deploy/nginx/portal.conf` (server-блок для
`/etc/nginx/conf.d/` на Astra Linux; при разворачивании поменять `/srv/portal`
на каталог с `manage.py`). Локальный `nginx-1.28.0/conf/nginx.conf` обновлён
теми же правилами с путями этой машины — но учтите: **весь каталог
`nginx-1.28.0/` в `.gitignore`**, поэтому правка только там не уезжает
дальше одного компьютера. Именно поэтому и появился отдельный файл в
репозитории.

Что добавлено: internal-локейшн `/protected/` с `alias` на MEDIA_ROOT (не на
`blobs/` — путь бы удвоился), `location /media/storage/ { deny all; }`,
`map $http_upgrade $connection_upgrade` вместо прошитого
`Connection "upgrade"` на всех проксируемых запросах, и
`client_max_body_size 110M` вместо 100M — тело multipart-запроса длиннее
самого файла, и при равных значениях файл ровно в 100 МБ
(`STORAGE_MAX_UPLOAD_SIZE`) отбивал бы nginx своей страницей 413 вместо
понятного сообщения от Django.

Проверено не только тестами: под `nginx + daphne` с `DEBUG=False` прямая
ссылка `/media/storage/blobs/<checksum>` отдаёт 403, `/protected/...` — 404,
`/media/avatar/../storage/blobs/<checksum>` — 403 (nginx нормализует URI до
выбора location), аватар по `/media/` — 200, а скачивание через
`/catalog/download/<id>/` возвращает 200 с `Server: nginx` и sha256 тела,
равным checksum blob'а. То есть файл отдаёт nginx, а не воркер Daphne.

Тесты — `storage/tests/test_x_accel_redirect.py` (15 штук): заголовок при
`DEBUG=False`, пустое тело ответа, имя файла, и отдельным классом — разбор
самих конфигов nginx.

### Картинки вне storage — файлы больше не переживают запись
Аватары, обложки, галерея, изображения постов и логотип сайта остаются
обычными `ImageField` (ARCHITECTURE.md, 1.1 — им не нужны ни права, ни TTL,
ни дедупликация), но за ними теперь убирают: `storage/mediafiles.py`,
регистрация — в `AppConfig.ready()` каждого приложения-владельца. Что важно
помнить:

- удаление идёт через `transaction.on_commit()`: откат вернул бы запись, а
  файл — нет;
- при замене файла удаляется прежний, и **проверка `update_fields`
  обязательна** — `UserActivityMiddleware` зовёт
  `save(update_fields=['last_activity'])` на каждый запрос;
- регистрировать `FileBlob.file` **нельзя**: на один файл ссылается
  несколько `FileObject`. Есть тест, который это стережёт;
- накопившееся убирает `manage.py media_verify [--delete-untracked]`; в
  `media/storage/` она не заглядывает — там своя команда `storage_verify`;
- список ссылок в ней собирается **по всем полям сразу**: каталоги вложены
  друг в друга (`gallery/thumbs/` внутри `gallery/`), и посчитай она каждый
  отдельно — живые миниатюры попали бы в мусор, а `--delete-untracked` их бы
  удалил. Поймано на боевом каталоге, закрыто тестом;
- каталоги `media/post_files/` и `media/Phonebook/` (наследство миграции на
  storage, раздел 11 ARCHITECTURE) ни одна из двух команд не трогает: они не
  принадлежат ни зарегистрированным полям, ни blob'ам. Разбирать их — руками
  и осознанно.

На момент подключения сверка нашла **59 файлов (41.7 МБ)** без единой ссылки
из БД: 14 аватаров, 17 в галерее, 27 у постов, 1 логотип. Физически они
удаляются только явным `--delete-untracked`.

### Сжатие изображений и миниатюры
`storage/images.py` + `IMAGE_MAX_SIDE` / `IMAGE_QUALITY` /
`IMAGE_THUMBNAIL_SIDE` в `settings.py`. Полное обоснование — ARCHITECTURE.md,
раздел 1.1. Коротко:

- работает на `gallery.GalleryImage` и `posts.PostImage` — у обеих появилось
  поле `thumbnail` и свойство `preview_url` (миниатюра, а если её нет —
  оригинал; нужно для снимков, загруженных до этой правки);
- вызов — в `save()` модели, и только для **нового** файла: признак
  `FieldFile._committed`. Уберёте проверку — каждое сохранение записи будет
  пересжимать уже сжатое;
- анимация не трогается, прозрачность не заливается чёрным, EXIF снимается
  (вместе с ориентацией — снимок с телефона иначе лежит на боку);
- если пересжатие не дало выигрыша, остаётся оригинал. Из-за этого тест на
  сжатие обязан брать **шумную** картинку: заливка и градиент жмутся в PNG
  до килобайтов, и функция честно отказывается работать, а выглядит это как
  поломка (см. `photo_bytes` в `test_image_processing.py`);
- одиночное фото в посте выводится оригиналом (оно во всю ширину карточки),
  миниатюра — в сетках из нескольких снимков и в галерее.

Замерено на живом стенде: 4000×3000 / 13.4 МБ → 1440×1920 / 1.18 МБ,
миниатюра 27 КБ, страница галереи грузит её, а не оригинал.

**Аватары и обложки пока не сжимаются** — те же две строки, если понадобится
(`User.avatar`, `User.cover`).

### Сироты в media/storage/blobs — убраны

## Структура организации (profiles) — должности, звания, телефоны

Не про storage, но живёт здесь же, потому что этот файл читают новые
сессии. Полное «почему» — в докстрингах `profiles/models.py` и
`profiles/forms.py`.

**Что было.** `User.position` и `User.rank` — свободный текст, `User.cat`
(подразделение) — FK, и все три стояли в форме настроек профиля. То есть
любой сотрудник мог вписать себе «Начальник организации» и перевести себя в
чужой отдел. Телефоны — пять полей `phone_pts/city/zs/9/hc` с подписями,
вшитыми в три шаблона, и масками ввода, вшитыми в `base.html`.

**Что стало.** Три справочника в админке + модель телефонов:

| Модель | Смысл |
|---|---|
| `Rank` | звание; сотрудник выбирает себе сам — оно не про подчинение |
| `Position` | должность; `parent` — иерархия, `department` — отдел, `max_holders` — сколько человек может занимать, `assignable_by_user` — можно ли выбрать себе самому |
| `PhoneType` | вид связи + **маска ввода** (маска — свойство вида, а не разметки) |
| `UserPhone` | номер конкретного сотрудника, `unique_together (user, type)` |

Решение владельца портала — вариант «флаг на справочнике»: руководящие
должности назначает только админ, рядовые сотрудник ставит себе сам.
Подразделение (`cat`) убрано из формы настроек по той же логике — это тоже
место в структуре, а не самоописание; в профиле оно показывается как
«Назначает администратор портала».

Грабли и следствия:

- **Миграция `0019` заводит пять видов связи** («Город», «HiCom», «ПТС»,
  «АТС-9», «ЗС») с масками из `base.html` — в **любой** свежей БД, включая
  тестовую. Тест про механику справочника обязан сначала очистить
  `PhoneType` (см. `PhoneDictionaryTestCase`), иначе ловит нарушение
  уникальности имени.
- Цепочка миграций: `0017` переименовывает старые текстовые поля →
  `0018` создаёт справочники и FK → `0019` переносит данные (в обе
  стороны) → `0020` убирает старые поля. Разбито на четыре шага не для
  красоты: смена типа поля с `CharField` на FK одной операцией на Postgres
  падает на приведении типа.
- В шаблонах `{{ user.position }}` и `{{ user.rank }}` работают как
  работали — `__str__` возвращает название, поэтому карточки сотрудников
  править не пришлось.
- Своя должность всегда остаётся в списке формы, даже если она не
  самоназначаемая: иначе сохранение настроек молча снимало бы человека с
  назначенной админом должности.
- Если самоназначаемых должностей нет вообще, поля в форме **нет** —
  контрол либо работает, либо его нет в разметке (ARCHITECTURE 12.4).

**Страница структуры** — `/structure/` (`OrgStructureView`, шаблон
`profiles/structure.html` + рекурсивный `includes/profile/org_position_node.html`),
пункт «Структура» в главном боковом меню. Дерево собирается во вьюхе одним
проходом по двум запросам, шаблон только рисует; узел включает сам себя,
поэтому глубина вложенности разметку не меняет. Защита от цикла стоит во
вьюхе, а не в шаблоне — там, где данные.

Два решения на этой странице, которые легко принять за недоделку:
вакансии показываются наравне с занятыми должностями (пустая клетка в
структуре — факт об организации), а сотрудники без должности выведены
отдельным блоком внизу (иначе человек, которому должность ещё не
назначили, просто отсутствовал бы на странице).

Ещё грабля: `includes/profile/org_position_node.html` содержит **свой**
`{% load static %}` — include не наследует загруженные библиотеки тегов, а
при рекурсивном включении это ещё и не сразу заметно.

Установлен по явному запросу (расписание должно работать одинаково на
Windows-разработке и Astra Linux-проде, без Task Scheduler/cron-развилки).
`django-celery-beat`, расписание хранится в БД. Периодические задачи на

|---|---|---|

Плюс async-таски без расписания, запускаются по требованию:

## Вёрстка — Midone theme, важные грабли

Источник макетов: `Midone-master/Midone v1.0.4/HTML Version/Compiled/`.
Пользователь несколько раз просил «пиксель в пиксель» — при расхождениях
**сверяться напрямую с файлом макета**, не с памятью о нём.

Каталог лежит на диске, но не в git (88 МБ). При уборке 14.08.2026 оставлен
намеренно — вёрстка берётся оттуда. Удалить его нельзя, восстановить из
репозитория не получится.

Найденные фактами (не догадкой) причины расхождений между нашей вёрсткой и
макетом:

1. **`data-feather` иконки не отрисовывались в Alpine-дропдаунах.**
   `feather.replace()` в `app.js` вызывается один раз при загрузке страницы,
   не видит содержимое, которое Alpine рендерит позже (`x-show`). Решение:
   inline-SVG вместо `<i data-feather>` — см. `includes/fm/icons.html`,
   вызывается как `{% include "includes/fm/icons.html" with icon='trash' cls='...' %}`.
   Набор иконок расширялся по ходу работы (`hard-drive`, `image` под
   «Просмотр» и т.д.) — если нужной иконки нет, дописать в этот файл, не
   заводить второй источник SVG.

2. **Сетка была 4 колонки вместо 6.** Макет использует `xxl:col-span-2`
   (порог 1600px). У нас между контентом и краем экрана есть боковое меню
   портала (~230px), которого нет в изолированном HTML-макете. Решение:
   продублировать те же пропорции на `xl:` (1280px) рядом с `xxl:`.

3. **Поле поиска выглядело иначе, чем в макете.** Tailwind/Flowbite
   перебивают `.input` из `app.css`. Решение: `static/midone/css/fm-overrides.css`,
   область действия ограничена классом `.fm-scope`.

4. **Многострочный `{# … #}` печатается на странице.** В Django эта форма
   комментария работает **только в одну строку**; многострочный вариант
   шаблонизатор комментарием не считает и выводит текстом прямо в вёрстку.
   Компиляция при этом не падает, ошибка тихая. Для многострочных —
   `{% comment %}`. Закрыто тестом
   `test_page_rendering.test_pages_do_not_leak_template_comment_syntax`,
   который проверяет, что в выводе любой страницы менеджера нет `{#`,
   `#}`, `{%`, `%}`, `{{`, `}}`.

5. **Две утилиты Tailwind на одно свойство — порядок решает не разметка.**
   `class="hidden … flex"` зависит от того, какое правило идёт позже в
   собранном CSS, а не от порядка классов в атрибуте. Где важна
   предсказуемость (подсказка дропзоны), заведена своя пара правил в
   `fm-overrides.css` с модификатором `is-visible`.

Файловые страницы (`exchange/folders.html`, `exchange/folder.html`,
`exchange/trash.html`, `catalog/folder.html`, `catalog/trash.html`,
`deptdocs/list.html`, `deptdocs/trash.html`, `storage/trash.html`,
`storage/dashboard.html`) используют общие partial'ы:

| Partial | Что |
|---|---|
| `includes/fm/menu.html` | левое меню разделов |
| `includes/fm/access_panel.html` | блок «Кому видно» внутри меню |
| `includes/fm/filter.html` | поиск + фильтр + select-all + сортировка + кнопки |
| `includes/fm/sort.html`, `includes/fm/select_all.html` | вкладываются в фильтр |
| `includes/fm/pagination.html` | страницы + «показывать по» |
| `includes/fm/bulk_bar.html` | панель массовых действий |
| `includes/fm/file_card.html`, `includes/fm/folder_card.html` | карточки |
| `includes/fm/icons.html` | inline-SVG |
| `<module>/_grid.html` | содержимое сетки, оно же ответ на `?partial=1` |

Корневой блок каждой страницы — `class="fm-scope grid grid-cols-12 gap-6 mt-8"`,
эти страницы **не используют** `sidebar_wrapper` из `base.html`.

Живое обновление подменяет `innerHTML` у `#fm-grid`, поэтому: всё, что
должно обновляться само, обязано лежать внутри `_grid.html`, а слушатели
событий — висеть на `document` или на контейнере, но не на самих

Главное боковое меню портала (`includes/layout/side_menu.html`) содержало
раскрывающийся пункт «Файлы» с тремя подпунктами — по прямому запросу

### Архитектурный долг — решено исправлять

Аудит приложений 14.08.2026. Владелец портала решил: **это чиним**. Список
не «на подумать», а план работы; порядок — по отношению пользы к риску.

Ядро (`storage` и три модуля-потребителя) в этот список не входит: границы
описаны, общий код вынесен, права проверяются. Проблемы — в приложениях,
которые достались проекту как есть и ни разу не пересматривались.

1. ~~**`_is_descendant` — три идентичные копии.**~~ **Сделано** (`3ad5eb54`):
   одна функция в `storage/utils.py`. Копий оказалось четыре — четвёртой был
   метод `Position._is_descendant` для дерева должностей.
2. ~~**`login`, `register` и `category` — приложения без моделей.**~~
   **Сделано** (`8428be15`, `4b1500f8`): вьюхи аутентификации в
   `profiles/views/auth.py`, `Category` — в `profiles/models.py`.
   Приложений стало 10 вместо 13. Три вьюхи `category` оказались
   обеднёнными копиями существующих страниц и схлопнуты в оригиналы.
   Историю миграций пришлось переписать: `profiles/0001_initial` и
   `deptdocs/0001_initial` ссылались на удаляемое приложение.
3. ~~**Шестьдесят почти одинаковых вьюх.**~~ **Сделано частично**
   (`7ef3ef5b`, `472affc7`): корзина, восстановление, окончательное
   удаление, скачивание и переименование — пять базовых классов в
   `storage/fmviews.py` вместо пятнадцати вьюх. Потребитель объявляет миксин
   с моделью и двумя хуками (`check_permission`, `notify`).

   Схлопывать перемещение файла и операции над папками **не стали
   намеренно**: там три разные политики (в каталоге папка-назначение
   необязательна, в deptdocs обязательна и проверяется, в обменнике смена
   папки меняет владельца), общего — шесть строк, и базовый класс с тремя
   хуками спрятал бы ровно то, что различается.
4. ~~**`profiles` — приложение-свалка.**~~ **Сделано** (`4c73a328`): модели
   и формы разложены по пакетам (`models/orgstructure|user|organizer|
   notifications|chat`, `forms/profile|auth|organizer`), как раньше вьюхи.

   Отдельными приложениями области не стали — тоже намеренно: `User` это
   `AUTH_USER_MODEL` и остаётся в profiles при любом раскладе, а перенос
   остальных моделей означал бы правку истории миграций у половины проекта
   ради выгоды, которой у внутреннего портала нет. Причина записана в
   докстринге `profiles/models/__init__.py`.

Заодно замечено, но отдельной работы не требует: URL всех приложений
подключены как `path('', include(...))` без `app_name`, имена маршрутов
глобальные; на каждой странице 5–6 одинаковых `SELECT` по `profiles_user`
(базовый шаблон и контекст-процессоры берут пользователя заново). Взрыва
N+1 нет — 13–25 запросов на страницу, но и данных в БД мало, так что N+1,
растущий с числом строк, на этих объёмах не проявился бы.

### Первое, за что стоит взяться
**Конвертация справочников в PDF.** Работа над справочниками разбита на два
шага, сделан только первый (меню, подписи, удаление, закрытие от анонимов).
Второй — чтобы Word и файлы Астра-офиса открывались на странице, а не
только скачивались. Требует LibreOffice на машине разработки: там он
выполняет ту же команду, что и на Астре, то есть проверка будет настоящей.

**Ждёт владельца, не разработчика:** первый обход сети на 10.10.0.0/24
(`manage.py scan_network`). Машина разработки в эту сеть не входит, и
только живой запуск покажет, режет ли их файрвол ICMP.

Архитектурный долг разобран: четыре пункта закрыты (два — частично и
осознанно, см. оговорки в каждом). Известного блокера прода нет, известных
дефектов кода нет. Перед разворачиванием на боевом сервере —
прод-конфигурация из «Осталось незакрытым».

Что стоит проверить руками перед реальным разворачиванием, потому что
тестами это не покрыть: `DEBUG = False` в `settings.py` (сейчас там жёстко
`True`, и именно по нему `get_download_response()` выбирает ветку с
`X-Accel-Redirect`), `SECRET_KEY` и пароль БД из окружения, а не из файла,
и подстановка реального пути вместо `/srv/portal` в
`deploy/nginx/portal.conf`.
