# Контекст для новых сессий — storage и файловые модули

Служебный файл, не документация проекта. Цель — дать новой сессии Claude
достаточно контекста без пересказа всей переписки. Архитектурные решения и
их обоснования — в `ARCHITECTURE.md` рядом с этим файлом; здесь только
состояние и то, что не попало бы в архитектурный документ.

## Что это за проект

Django 5.0.1 + Channels/Daphne (ASGI) внутренний портал организации
(«Сеть-УК»). Windows-разработка (`c:\Users\User\Desktop\social_network`),
прод предполагается на Astra Linux. Git user `DreemzDev`, ветка `main`.

Реальное окружение: PostgreSQL (`portal`/`postgres`/`123`@127.0.0.1:5432),
Redis для Channels и Celery (`db=1` для Celery, чтобы не смешивать с
WS-трафиком). Виртуальное окружение — `.venv` в корне репозитория (НЕ `venv`,
тот путь битый и упоминается только в устаревшем `start_server.bat`).

Способ запуска. **Redis нужен первым** — на нём и Channels (живые
обновления, чат), и Celery; без него страницы откроются, но живые
обновления и массовые операции работать не будут:

```powershell
# 1. Redis (установлен в C:\Redis, автозапуска нет)
Start-Process -FilePath "C:\Redis\redis-server.exe" -WindowStyle Hidden
```

```bash
# 2. Сам портал (ASGI — обязателен для WebSocket, runserver не подходит)
cd c:/Users/User/Desktop/social_network/social_network
../.venv/Scripts/daphne.exe -b 127.0.0.1 -p 8000 social_network.asgi:application

# 3. Воркер — для массовых операций и очистки корзины. Без него bulk-запрос
#    вернёт task_id, задача не выполнится, а фронт будет опрашивать PENDING
#    бесконечно.
../.venv/Scripts/celery.exe -A social_network worker --loglevel=info --pool=solo

# 4. Beat — только если нужны периодические задачи по расписанию
../.venv/Scripts/celery.exe -A social_network beat --loglevel=info
```

```powershell
# 5. nginx — только когда нужно проверить прод-путь отдачи файлов
#    (X-Accel-Redirect, запрет /media/storage/). В обычной разработке не
#    нужен: при DEBUG=True файл отдаёт сам Django.
$nginx = "C:\Users\User\Desktop\social_network\social_network\nginx-1.28.0"
& "$nginx\nginx.exe" -p $nginx -t          # проверить конфиг
Start-Process "$nginx\nginx.exe" -ArgumentList "-p","." -WorkingDirectory $nginx
& "$nginx\nginx.exe" -p $nginx -s stop     # остановить
```

Проверять прод-путь надо при `DEBUG=False`, иначе ветка с `X-Accel-Redirect`
просто не выполняется. Менять `settings.py` ради этого не нужно — достаточно
временного модуля рядом и переменных окружения:

```bash
# settings_prodcheck.py:  from social_network.settings import *  /  DEBUG = False
DJANGO_SETTINGS_MODULE=settings_prodcheck PYTHONPATH="<каталог с модулем>;." \
    ../.venv/Scripts/daphne.exe -b 127.0.0.1 -p 8000 social_network.asgi:application
```

Daphne **не перезагружается сам** при изменении Python-кода — после правки
вьюх/моделей/urls его надо перезапускать. Шаблоны при `DEBUG=True`
подхватываются без перезапуска (кеширующего загрузчика нет).

## Модуль storage — единый сервис хранения файлов

Полное архитектурное обоснование — `apps/storage/ARCHITECTURE.md` (читать
его, если нужно понять «почему», не «что»). Коротко: `FileBlob` (физическое
содержимое, `checksum` unique, дедупликация) + `FileObject` (именованное
использование, на него ссылаются потребители). Права доступа — не в storage,
их проверяет каждый модуль-потребитель сам.

Ключевые баги, найденные аудитом и исправленные (тесты в `apps/storage/tests/`):

1. **`_object_has_references()` всегда возвращала `False`** — обходила
   `FileObject._meta.get_fields()`, но все потребители используют
   `related_name='+'`, который подавляет обратные связи. Исправлено на обход
   `apps.get_models()`. Тест: `test_references.py`.
2. **Прямой доступ к файлам в обход прав** — `/media/storage/blobs/<checksum>`
   раздавался как обычная медиатека. Закрыто перехватчиком `^media/storage/`
   в корневом `urls.py` (404 до `static()`). Тест: `test_direct_access.py`.
3. **Автоочистка по TTL не работала** — `purge_expired_objects()` в storage
   вызывала `detach()`, который защищал файлы с живыми ссылками, но функция
   отчитывалась об успехе, не удалив ничего. Убрана из storage; каждый
   потребитель, которому нужен TTL, пишет свою periodic task (см.
   `exchange.tasks.cleanup_expired_exchange_files`).
4. **Каскадное удаление обходило `detach()`** — чек-лист требовал ручного
   вызова `detach()`, но каскад от FK сносит запись потребителя сам, и
   вызвать его некому. Реальные пути: `CatalogFolder` → `CatalogDocument`,
   `DepartmentFolder` → `DepartmentDocument`, деревья папок через `parent`
   (включая `ExchangeFolder`, добавленную позже), `User` → `ExchangeFile`
   (`owner`). Blob оставался `ACTIVE` без ссылок навсегда. Исправлено
   сигналом `post_delete` в `storage/signals.py` — `detach()` выполняется
   автоматически для всех потребителей (интроспекция та же, что в 5.2).
   Атрибуция «кто удалил» передаётся пометкой `attribute_deletion()` перед
   `delete()`. Подробности — ARCHITECTURE.md, раздел 5.5. Тесты:
   `test_cascade.py`, `test_consumers.py`, `test_exchange_folders.py`.
5. **`StorageService.get_storage_stats()` падал с `NameError`** —
   использовал `models.Count()` без импорта `models` (был только
   `from django.db.models import Sum`). Ловилось только при заходе персонала
   (`is_staff`) на `/storage/` — обычные пользователи эту ветку не видели,
   баг был бы незаметен до первой жалобы. Исправлено импортом `Count`.
6. **`Content-Disposition` с кириллицей ломался на прод-пути.** Имя
   подставлялось в заголовок как есть, а `HttpResponse` кодирует значение
   вне latin-1 по RFC 2047 (`=?utf-8?b?…?=`) — форму, которой
   `Content-Disposition` не знает. Браузер сохранил бы файл под base64-строкой
   или под именем-хэшем из URL. Задевало почти каждое скачивание (имена в
   портале кириллические) и **только прод**: в ветке `DEBUG` заголовок
   собирает `FileResponse`, который сам оформляет имя по RFC 5987. Найдено
   при написании теста на `X-Accel-Redirect`, исправлено там же.
   Тест: `test_x_accel_redirect.py`.

Гонки на конкурентную загрузку/purge проверены на **реальном Postgres**
(`storage/tests/test_concurrency.py`) — на SQLite `select_for_update` и
`pg_advisory_xact_lock` не работают как надо, тесты были бы декоративными.

### Как запускать тесты — грабли

Приложения лежат в `apps/`, которая добавлена в `sys.path`, поэтому метка
теста — `storage`, а **не** `apps.storage` (с последней unittest падает в
discovery с `TypeError: path should be string... not NoneType`).

```bash
cd c:/Users/User/Desktop/social_network/social_network
../.venv/Scripts/python.exe manage.py test storage --top-level-directory=apps
```

`.venv` лежит в корне репозитория, а `manage.py` — во вложенном
`social_network/`, поэтому из каталога с `manage.py` путь к интерпретатору
именно `../.venv/...`, а не `.venv/...`.

Голый `manage.py test` без аргументов находит **0 тестов** — discovery
стартует из корня проекта и в `apps/` не заходит. Все реальные тесты в
проекте лежат в `apps/storage/tests/` (**192 штуки** на момент написания);
`tests.py` в остальных приложениях — пустые заглушки Django. Тесты трогают
`exchange`/`catalog`/`deptdocs`/`profiles.Notification` напрямую, поэтому
метка `storage` тянет за собой их модели — так и задумано, отдельная
тестовая инфраструктура для каждого модуля не заводилась.

**Нужен поднятый Redis.** Часть тестов проходит через `notify()`, который
пушит событие в Channels, а тот идёт в Redis. Без него падает ~40 тестов
с `ConnectionError ... 6379`, и выглядит это как поломка кода, хотя дело
в окружении. Redis установлен в `C:\Redis`, поднимается так:

```powershell
Start-Process -FilePath "C:\Redis\redis-server.exe" -WindowStyle Hidden
```

Живые обновления файлового менеджера (`storage/realtime.py`) при упавшем
Redis, в отличие от `notify()`, ошибку не выбрасывают — пишут warning в
лог и продолжают (тест `test_fm_ui_layer.RealtimeBroadcastTest`).
`profiles.views._common.notify()` так не умеет — это старое поведение,
которое при падении Redis превращает успешное действие в 500; сюда стоит
вернуться отдельно.

**Тесты пишут медиа во временный каталог.** В `settings.py` под
`'test' in sys.argv` `MEDIA_ROOT` подменяется на `tempfile.mkdtemp()`.
Причина не косметическая: Django удаляет тестовую БД, но не файлы, и пока
каталог был общий с боевым, каждый прогон оставлял blob'ы в
`media/storage/blobs/` навсегда — накопилось 2887 файлов при 25 записях в
БД. Заодно это ломало дедупликацию **внутри** прогона: БД между тестами
откатывается, а файл остаётся, поэтому следующая загрузка того же
содержимого получала от `FileSystemStorage` имя с суффиксом
(`<checksum>_B24AkEu`).

Отсюда правило: **тест, который проверяет состояние диска, обязан брать
свой `MEDIA_ROOT` на каждый тест** (`override_settings` в `setUp`, см.
`test_deduplication.DeduplicationTest`). Общего каталога на прогон
недостаточно.

**`CELERY_TASK_ALWAYS_EAGER = 'test' in sys.argv`** в `settings.py` —
под `manage.py test` Celery-таски (`bulk_move_documents`,
`bulk_trash_documents`) выполняются синхронно в том же процессе, без
поднятого Redis/worker'а. Рядом же `CELERY_TASK_STORE_EAGER_RESULT` —
без него `AsyncResult(task_id).state` в eager-режиме не видит финальный
`SUCCESS` (Celery по умолчанию не пишет результат eager-задачи в backend).
Оба флага завязаны на один и тот же `'test' in sys.argv`, руками
переключать не нужно.

## Потребители storage (текущее состояние)

| Модуль | Модель | Права | TTL |
|---|---|---|---|
| `exchange` | `ExchangeFile` (+ `ExchangeFolder` для подпапок) | папка = пользователь, видит и пишет любой, удаляет владелец папки/подпапки или загрузивший/создавший | 7 дней (`exchange.tasks`), включая корзину |
| `catalog` | `CatalogFolder` + `CatalogDocument` | видно всем аутентифицированным | нет TTL, но корзина автоочищается через 30 дней |
| `deptdocs` | `DepartmentFolder` + `DepartmentDocument` | `allowed_users` M2M на конкретных людей, любой участник равноправен | нет TTL, корзина — 30 дней |
| `posts` | `PostFile` | видно всем, кто видит пост | нет |
| `phonebook` | `Phonebook.file_object` | как раньше (публично) | нет |

`posts.PostImage`, `gallery.GalleryImage`, `profiles.User.avatar/cover` —
**намеренно не в storage**, обычные `ImageField` (нет прав/TTL/шаринга, см.
ARCHITECTURE.md раздел 1.1).

### exchange — важно про модель

Изначально был «файл адресован конкретному получателю» (как email-вложение),
потом переделан в открытую сетевую папку: папка = пользователь (нет
отдельной модели корневой папки), содержимое видно всем, удалять может
владелец папки или тот, кто загрузил.

**Подпапки (`ExchangeFolder`) добавлены позже, отдельным заходом.** Первая
версия ошибочно ограничивала создание/удаление подпапок только владельцем
личной папки — по аналогии с `deptdocs.DepartmentFolder`. Пользователь это
поправил: обменник открыт на запись всем, значит и подпапки должны быть
такими же — создать может кто угодно, удалить может владелец личной папки
или тот, кто создал подпапку (`ExchangeFolder.can_be_deleted_by`, тот же
принцип, что и у файлов). Если в коде/истории видите `can_be_managed_by`
или проверку `owner == request.user` на создание подпапки — это
промежуточное ошибочное состояние, актуальный метод —
`can_be_deleted_by`.

### deptdocs — важно про модель

Документ сам не хранит прав — наследует их от `folder.allowed_users` (M2M
на конкретных людей, не отделы). Любой сотрудник может создать папку и
раздать доступ; любой участник равноправен с создателем, включая право
убрать самого себя (после чего мгновенно теряет видимость папки).

Найденный и исправленный баг: модалка «Доступ к папке» использовала ту же
переменную контекста `all_users`, что и модалка создания папки (там она
намеренно исключает текущего пользователя — «кому дать доступ, кроме
вас»). В модалке *редактирования* доступа существующей папки это давало
силовой баг: создатель не видел себя в списке чекбоксов, хотя реально
состоял в `allowed_users`, и при сохранении формы **терял себе доступ** —
его pk физически не мог попасть в отправленный список. Исправлено
разделением на `all_users_except_me` (создание) и `all_users` (просмотр
существующего доступа, полный список).

## Функционал файлового менеджера — что и зачем

Всё перечисленное ниже уже в `main`. Раздел нужен не как список задач, а
как карта: по каким ключевым словам искать нужное место и какое решение
за каждым пунктом стоит.

### 1. Подпапки обменника (`ExchangeFolder`)
Модель + миграция `0003_exchangefolder_exchangefile_folder.py`. Права —
см. раздел выше.

### 2. Единая страница корзины с табами
`/storage/trash/` (`storage.views.UnifiedTrashView`, шаблон
`templates/storage/trash.html`) — раньше у каждого модуля была отдельная
корзина по своему адресу, визуально неотличимая от других (тот же layout,
тот же заголовок «Корзина»). Легко было открыть не ту и решить, что файл
пропал. Новая страница собирает все три queryset'а (с теми же правилами
видимости, что и в отдельных `TrashView`) на одной странице, табы Alpine.
Старые адреса (`exchange_trash`, `catalog_trash`, `deptdocs_trash`) не
удалены, работают как есть — `fm_menu.html` теперь ссылается на
`storage_trash`.

### 3. Dashboard занятого места
`/storage/` (`StorageDashboardView`) — своя квота с прогресс-баром,
сводка по всему хранилищу для персонала (`get_storage_stats()`, см. баг
№5 выше), кнопка «Очистить сейчас» для каждой корзины.

### 4. Автоочистка корзины по сроку (catalog, deptdocs)
Раньше была только у обменника (TTL от даты загрузки, случайно захватывает
и корзину). У каталога и приватного доступа автоочистки корзины не было
вообще — удалённое лежало там неограниченно. Добавлены
`catalog.tasks.cleanup_catalog_trash` / `deptdocs.tasks.cleanup_deptdocs_trash`,
`STORAGE_TRASH_RETENTION_DAYS = 30`, periodic tasks заведены дата-миграциями
по образцу `storage/migrations/0002_seed_periodic_tasks.py`.

### 5. Переименование, перемещение, копирование/пересылка
Rename и move — для файлов и папок во всех трёх модулях, с защитой от
циклов в дереве (`_is_descendant`) и проверкой прав/принадлежности папки.
Пересылка между разделами — `StorageService.copy_reference()`: новый
`FileObject` на **тот же** blob, без повторной записи на диск (не
`upload()` — там дедупликация уже не нужна, содержимое и так на месте).
Проверяет квоту получателя по `blob.size`, но не задваивает её, если
получатель уже "владеет" этим blob'ом.

### 6. Массовые операции — асинхронно через Celery
Bulk move/trash во всех трёх модулях уходят в `storage.tasks.bulk_move_documents`
/ `bulk_trash_documents` — батчами по 200, с `update_state(state='PROGRESS', ...)`.
Вьюхи возвращают `{'task_id': ...}` вместо готового результата. Опрос —
`/storage/task-status/<task_id>/` (`TaskStatusView`), общий для всех
модулей, polling с фронта (`fm-actions.js: fmPollTaskStatus`).

Право на удаление/перенос там, где оно не сводится к простому dict-фильтру
(`Q(owner=X) | Q(uploaded_by=X)` в обменнике), проверяется **во вьюхе до**
постановки задачи — задаче передаётся уже урезанный список id, сама задача
никаких прав не проверяет.

### 7. Уведомления о новых файлах
`profiles.Notification` получил `Kind.FILE_SHARED` и новое поле `url`
(миграция `0016_notification_url_alter_notification_kind.py`) — готовая
ссылка вместо FK на конкретный объект, потому что файл может быть в любом
из трёх модулей. `notify()` в `profiles/views/_common.py` принимает
`url=''`. Обменник уведомляет владельца папки при загрузке чужим
человеком (не себя), приватный доступ — всех участников `allowed_users`
кроме загрузившего. Каталог никого не уведомляет — общедоступен, рассылка
всем при каждой загрузке была бы шумом.

Живой JS в `base.html` (`prependNotificationItem`) раньше игнорировал
`url` в приходящем по WebSocket уведомлении — клик по свежему
уведомлению никуда не вёл, хотя статический список (`notification_center_items`)
уже поддерживал ссылки. Исправлено.

### 8. Сортировка и превью
`storage/utils.py: apply_sort()` — общий хелпер для `?sort=name/-name/
uploaded_at/-uploaded_at/size/-size`, недопустимые значения падают на
дефолт (`-uploaded_at`), не долетая до `order_by()` напрямую. Сортировка
по размеру идёт через `file_object__blob__size` — `FileObject.size` это
python-property, ORDER BY по нему на уровне SQL невозможен.

Превью в браузере — `?inline=1` на всех трёх download-эндпоинтах,
использует уже существовавший `StorageService.get_download_response(inline=True)`
(раньше применялся только для `phonebook`).

### 9. Общий JS-модуль `static/js/fm-actions.js`
Один файл на все три модуля вместо копии одного и того же кода в каждом
шаблоне. Публичный API — объект `window.FM`:

| Метод | Назначение |
|---|---|
| `FM.init(config)` | точка входа: выделение, массовые кнопки, drag&drop, WebSocket |
| `FM.action(url, data, opts)` | POST + тост + обновление сетки; единственный правильный способ дёрнуть эндпоинт |
| `FM.refresh()` / `FM.navigate(url)` | перерисовать сетку / перейти по странице без reload |
| `FM.confirm({...})` | модалка подтверждения вместо `confirm()` |
| `FM.toast(text, type)` | тост темы Midone (`$.toast` из её бандла) |
| `FM.upload(url, formData, opts)` | XHR — только он даёт `upload.onprogress` |
| `FM.pollTask(id, opts)` | опрос статуса Celery-задачи |

Действия карточек объявляются **декларативно на самой кнопке**
(`data-fm-action`, `data-fm-url`, `data-fm-confirm`, `data-fm-success`,
`data-fm-remove-card`) и обрабатываются одним делегатом на `document` —
поэтому те же кнопки работают и на страницах корзины, где сетки нет.
Подключается через `{% block extra_js %}` только на файловых страницах.

### Известные упрощения, не доведённые до конца
- Массового скачивания zip нет вообще — требует стриминга из storage «на
  лету», не реализовывалось.
- Сам JS (`fm-actions.js`) юнит-тестами не покрыт: проверяется серверная
  часть, от которой он зависит (рендер страниц, `?partial=1`, эндпоинты),
  но не поведение в браузере — JS-раннера в проекте нет.
- Перетаскивание работает на загрузку в текущую папку; перетаскивания
  карточки в папку (move drag&drop) нет.
- Папки не участвуют в массовых операциях (чекбокса у них нет намеренно):
  bulk-задачи работают над одной моделью, а папка — поддерево, и «удалить
  выбранное» означало бы разную семантику для разных элементов выделения.
  Перенос и удаление папки — поштучно, через её меню.
- У корзины массового восстановления/очистки нет, только поштучно.

### Перенос папок
Пункт «Переместить» есть у карточки папки во всех трёх модулях. У каталога

новый родитель в дереве, а не папка-контейнер). Массовый перенос
использует ту же модалку со значением `moveTarget = 'bulk'`.

### Что было исправлено попутно
- **Утечка в приватном доступе**: список вложенных подпапок не
  фильтровался по доступу — были видны названия закрытых папок. На
  корневом уровне фильтр был, на вложенном нет.
- **Удаление папки шло мимо корзины** во всех трёх модулях (см.
  ARCHITECTURE.md 12.3). У каталога и приватного доступа удаления папок из
  UI вообще не было.
- **`copy_reference()` без блокировки blob'а** — гонка с `detach()`
  оставляла живую ссылку на blob в статусе ORPHAN.
- **Настройки storage читались при импорте модуля** — `override_settings`
  не работал, квота требовала рестарта.
- **`TaskStatusView` падал с TypeError** на задачах, возвращающих число
  (очистка корзины возвращает int, а не dict) — проявилось, когда очистку
  перевели с синхронного вызова на `.delay()`.
- **Мультизагрузка обрывалась на первой ошибке**, отвечая 400, хотя часть
  файлов уже была загружена.
- Мёртвые контролы (расширенный фильтр, селектор размера страницы,
  чекбоксы папок, «Настройки», метки в меню) — либо сделаны рабочими,
  либо убраны. Действует правило: **контрол либо работает, либо его нет в
  разметке** (ARCHITECTURE.md, 12.4).
- **Пагинация вставала сбоку от файлов**: она лежала внутри
  grid-контейнера и потому становилась такой же ячейкой сетки, как
  карточка. Сетка карточек и пагинация разведены в соседние блоки —
  если правите `_grid.html`, не заворачивайте пагинацию обратно внутрь
  `grid grid-cols-12`.

### Осталось незакрытым (важно)
- `notify()` в `profiles/views/_common.py` не устойчив к падению Redis
  (см. раздел про тесты выше).
- `TaskStatusView` отдаёт статус задачи любому аутентифицированному по
  `task_id`, без проверки, он ли её запускал. Идентификаторы — uuid4, так
  что угадать нельзя, но владения не проверяется; в payload только
  счётчики.
- **`?inline=1` доверяет MIME-типу из аплоада.** `blob.mime_type`
  определяется по загруженному файлу, а `get_download_response(inline=True)`
  отдаёт его как есть. Загруженный `.html` откроется в браузере как
  страница в домене портала — то есть хранимая XSS. В интерфейсе пункт
  «Просмотр» показывается только для типов из `fm_tags.is_previewable`, но
  сам эндпоинт принимает `inline=1` для чего угодно. Чинится на стороне
  Django (белый список MIME для inline), не в nginx.

### nginx — закрыто

Прод-конфигурация приведена в порядок. Канонический конфиг лежит **в git**:
`social_network/deploy/nginx/portal.conf` (server-блок для
`/etc/nginx/conf.d/` на Astra Linux; при разворачивании поменять `/srv/portal`
на каталог с `manage.py`). Локальный `nginx-1.28.0/conf/nginx.conf` обновлён
теми же правилами с путями этой машины — но учтите: **весь каталог
`nginx-1.28.0/` в `.gitignore`**, поэтому правка только там не уезжает
дальше одного компьютера. Именно поэтому и появился отдельный файл в
репозитории.

Что добавлено: internal-локейшн `/protected/` с `alias` на MEDIA_ROOT (не на
`blobs/` — путь бы удвоился), `location /media/storage/ { deny all; }`,
`map $http_upgrade $connection_upgrade` вместо прошитого
`Connection "upgrade"` на всех проксируемых запросах, и
`client_max_body_size 110M` вместо 100M — тело multipart-запроса длиннее
самого файла, и при равных значениях файл ровно в 100 МБ
(`STORAGE_MAX_UPLOAD_SIZE`) отбивал бы nginx своей страницей 413 вместо
понятного сообщения от Django.

Проверено не только тестами: под `nginx + daphne` с `DEBUG=False` прямая
ссылка `/media/storage/blobs/<checksum>` отдаёт 403, `/protected/...` — 404,
`/media/avatar/../storage/blobs/<checksum>` — 403 (nginx нормализует URI до
выбора location), аватар по `/media/` — 200, а скачивание через
`/catalog/download/<id>/` возвращает 200 с `Server: nginx` и sha256 тела,
равным checksum blob'а. То есть файл отдаёт nginx, а не воркер Daphne.

Тесты — `storage/tests/test_x_accel_redirect.py` (15 штук): заголовок при
`DEBUG=False`, пустое тело ответа, имя файла, и отдельным классом — разбор
самих конфигов nginx.

### Сироты в media/storage/blobs — убраны
Было 2887 файлов при 25 записях `FileBlob`. `storage_verify --delete-untracked`
удалил 2862, осталось ровно 25, повторный `storage_verify` чист. Команда
необратима — перед повторным применением стоит сверить, что число «лишних»
совпадает с разницей «файлы на диске минус `FileBlob.objects.count()`».

### Проверено фактически (не по документации)
Дедупликация работает физически, а не только на уровне записей: на боевой
БД 25 `FileBlob` на 29 `FileObject`, один blob обслуживает 7 ссылок
(`welcom.jpg`), имя файла на диске равно checksum. Покрыто
`test_deduplication.py` — включая то, что вторая загрузка того же
содержимого не пишет на диск ничего.

## Вёрстка — Midone theme, важные грабли

Источник макетов: `Midone-master/Midone v1.0.4/HTML Version/Compiled/`.
Пользователь несколько раз просил «пиксель в пиксель» — при расхождениях
**сверяться напрямую с файлом макета**, не с памятью о нём.

Найденные фактами (не догадкой) причины расхождений между нашей вёрсткой и
макетом:

1. **`data-feather` иконки не отрисовывались в Alpine-дропдаунах.**
   `feather.replace()` в `app.js` вызывается один раз при загрузке страницы,
   не видит содержимое, которое Alpine рендерит позже (`x-show`). Решение:
   inline-SVG вместо `<i data-feather>` — см. `includes/fm_icons.html`,
   вызывается как `{% include "includes/fm_icons.html" with icon='trash' cls='...' %}`.
   Набор иконок расширялся по ходу работы (`hard-drive`, `image` под
   «Просмотр» и т.д.) — если нужной иконки нет, дописать в этот файл, не
   заводить второй источник SVG.

2. **Сетка была 4 колонки вместо 6.** Макет использует `xxl:col-span-2`
   (порог 1600px). У нас между контентом и краем экрана есть боковое меню
   портала (~230px), которого нет в изолированном HTML-макете. Решение:
   продублировать те же пропорции на `xl:` (1280px) рядом с `xxl:`.

3. **Поле поиска выглядело иначе, чем в макете.** Tailwind/Flowbite
   перебивают `.input` из `app.css`. Решение: `static/midone/css/fm-overrides.css`,
   область действия ограничена классом `.fm-scope`.

4. **Многострочный `{# … #}` печатается на странице.** В Django эта форма
   комментария работает **только в одну строку**; многострочный вариант
   шаблонизатор комментарием не считает и выводит текстом прямо в вёрстку.
   Компиляция при этом не падает, ошибка тихая. Для многострочных —
   `{% comment %}`. Закрыто тестом
   `test_page_rendering.test_pages_do_not_leak_template_comment_syntax`,
   который проверяет, что в выводе любой страницы менеджера нет `{#`,
   `#}`, `{%`, `%}`, `{{`, `}}`.

5. **Две утилиты Tailwind на одно свойство — порядок решает не разметка.**
   `class="hidden … flex"` зависит от того, какое правило идёт позже в
   собранном CSS, а не от порядка классов в атрибуте. Где важна
   предсказуемость (подсказка дропзоны), заведена своя пара правил в
   `fm-overrides.css` с модификатором `is-visible`.

Файловые страницы (`exchange/folders.html`, `exchange/folder.html`,
`exchange/trash.html`, `catalog/folder.html`, `catalog/trash.html`,
`deptdocs/list.html`, `deptdocs/trash.html`, `storage/trash.html`,
`storage/dashboard.html`) используют общие partial'ы:

| Partial | Что |
|---|---|
| `includes/fm_menu.html` | левое меню разделов |
| `includes/fm_access_panel.html` | блок «Кому видно» внутри меню |
| `includes/fm_filter.html` | поиск + фильтр + select-all + сортировка + кнопки |
| `includes/fm_sort.html`, `includes/fm_select_all.html` | вкладываются в фильтр |
| `includes/fm_pagination.html` | страницы + «показывать по» |
| `includes/fm_bulk_bar.html` | панель массовых действий |
| `includes/fm_file_card.html`, `includes/fm_folder_card.html` | карточки |
| `includes/fm_icons.html` | inline-SVG |
| `<module>/_grid.html` | содержимое сетки, оно же ответ на `?partial=1` |

Корневой блок каждой страницы — `class="fm-scope grid grid-cols-12 gap-6 mt-8"`,
эти страницы **не используют** `sidebar_wrapper` из `base.html`.

Живое обновление подменяет `innerHTML` у `#fm-grid`, поэтому: всё, что
должно обновляться само, обязано лежать внутри `_grid.html`, а слушатели
событий — висеть на `document` или на контейнере, но не на самих
карточках (они пересоздаются).

Главное боковое меню портала (`includes/side_menu.html`) содержало
раскрывающийся пункт «Файлы» с тремя подпунктами — по прямому запросу
пользователя схлопнут в один пункт «Файловый менеджер», ведущий на
обменник; вся навигация между разделами теперь только внутри
`fm_menu.html` (там же добавлены пункты «Корзина» → `storage_trash` и
«Занятое место» → `storage_dashboard`).

Разделы `fm_menu.html` переименованы по запросу пользователя: «Обменник» /
«Информационный каталог» (было «Каталог») / «Приватный доступ» (было
«Документы отдела»); «Справочник» убран из этого меню — остаётся отдельным
пунктом в главном боковом меню портала, файловым менеджером не считается.

Был временный эталонный маршрут `/fm-reference/` для визуальной сверки —
**удалён** после того как вёрстка сошлась. Если понадобится пересобрать —
брать `simple-menu-file-manager.html` из папки макета.

## Как продолжать в новой сессии

1. Прочитать `apps/storage/ARCHITECTURE.md` — там «почему» для storage;
   разделы 12.1–12.4 описывают слой интерфейса файлового менеджера.
2. Прочитать этот файл — «что уже сделано и на чём споткнулись».
3. `git log --oneline -10` и `git status` — проверить реальное состояние.
   Не доверять числу тестов и списку коммитов из этого документа
   буквально: он описывает срез на момент написания.
4. Поднять Redis (`C:\Redis\redis-server.exe`) до запуска сервера и до
   прогона тестов — иначе ~40 тестов упадут на `ConnectionError`, и это
   выглядит как поломка кода.
5. При работе с вёрсткой файловых страниц — сверяться с оригиналом в
   `Midone-master/.../Compiled/simple-menu-file-manager.html`, не с памятью.
6. При работе со storage — гонки и права проверять на Postgres, не на
   SQLite (`manage.py test` в этом проекте настроен на реальный Postgres).
7. Перед тем как советовать конкретный код по памяти этого файла —
   проверить, что упомянутая функция/файл всё ещё существует (`grep`,
   `Read`), а не полагаться на то, что здесь написано.

select-all, drag&drop загрузка, хлебные крошки на весь путь, перенос и
удаление папок, «удалится через N дней» в корзине, превью только для
открываемых браузером типов, блок «Кому видно» — всё это в `main`.
