# Сеть-УК — корпоративная соцсеть

Django-приложение для внутренней сети компании: лента постов, профили сотрудников,
мессенджер в реальном времени, личные задачи/заметки/календарь, справочник телефонов,
галерея. Работает в изолированной сети без доступа в интернет — все статические
библиотеки (Tailwind, jQuery, Alpine.js, Flowbite, Lightbox) вендорятся локально,
никаких CDN-подключений в шаблонах.

Этот файл — карта проекта для разработчика или ИИ-агента, впервые открывающего
репозиторий: что где лежит, как связаны приложения, какие есть неочевидные
архитектурные решения и почему они такие.

## Быстрый старт

```bash
# Запускать из этой же папки (здесь лежит manage.py). venv — в ../.venv
../.venv/Scripts/python.exe manage.py migrate
../.venv/Scripts/python.exe manage.py runserver   # обычный HTTP, без WebSocket

# Полноценный запуск с WebSocket (мессенджер, живые комментарии) — через Daphne (ASGI)
../.venv/Scripts/daphne.exe -b 127.0.0.1 -p 8000 social_network.asgi:application
```

Требуется запущенный Redis на `127.0.0.1:6379` — используется как backend для
Channels (`CHANNEL_LAYERS` в `settings.py`). Без Redis WebSocket-функциональность
(чат, живые комментарии, уведомления) не заработает.

**После любого изменения кода, затрагивающего WebSocket-consumer'ы, нужно
перезапускать Daphne** — `runserver` их не подхватывает (это ASGI-only функциональность).

## Структура репозитория

Этот README лежит в корне Django-проекта (там же, где `manage.py`) — папка,
на которую указывает дерево ниже:

```
.                                   ← вы здесь, manage.py и README.md рядом
├── social_network/                ← пакет настроек проекта
│   ├── settings.py
│   ├── urls.py                    ← корневой urlconf, include() всех apps
│   ├── asgi.py                    ← РЕАЛЬНАЯ точка входа для WebSocket (см. ниже)
│   └── routing.py                 ← альтернативный WS-роутинг, НЕ используется в проде
├── apps/                          ← все Django-приложения проекта
│   ├── profiles/                  ← сердце проекта: юзер, чат, задачи, заметки, календарь
│   ├── posts/                     ← лента ("Новости") + "Моя страница"
│   ├── comments/                  ← комментарии к постам (+ живые обновления, лайки)
│   ├── category/                  ← категории для постов/пользователей/телефонов
│   ├── gallery/                   ← общая фотогалерея
│   ├── login/, register/          ← вход, регистрация, сброс пароля
│   ├── phonebook/                 ← справочник телефонов сотрудников
│   └── sitesettings/              ← глобальные настройки сайта (логотип, название и т.п.)
├── templates/                     ← все HTML-шаблоны проекта (общие на все apps)
├── static/                        ← вендоренные библиотеки + собственные JS/CSS/img
└── media/                         ← загружаемые пользователями файлы (аватары, посты и т.д.)
```

Django-приложения физически лежат в `apps/`, но `settings.py` добавляет эту папку в
`sys.path`, поэтому импортируются они без префикса: `from profiles.models import ...`,
а не `from apps.profiles.models import ...`. Это касается и `INSTALLED_APPS`
(`'profiles.apps.ProfilesConfig'`, не `'apps.profiles...'`).

### ⚠️ Ловушка: `asgi.py` vs `routing.py`

В `social_network/` есть два файла с настройкой WebSocket-маршрутов:
`asgi.py` и `routing.py`. **Реальная точка входа — `asgi.py`** (Daphne запускается
как `social_network.asgi:application`, `settings.ASGI_APPLICATION` на неё не влияет,
когда сервер стартует явным путём через CLI). Файл `routing.py` — более старая
заготовка, `settings.ASGI_APPLICATION` на неё ссылается, но при текущем способе
запуска (Daphne + явный путь к `asgi:application`) она не используется.

**Если добавляете новый WebSocket-consumer — регистрируйте маршрут в `asgi.py`.**
Держите `routing.py` синхронным на всякий случай, но не полагайтесь на него —
эта рассинхронизация уже один раз стоила часа отладки (маршрут был добавлен только
в `routing.py`, WebSocket падал с `No route found`).

Текущие WebSocket-каналы (все зарегистрированы в обоих файлах):

| Путь | Consumer | Группа Channels | Назначение |
|---|---|---|---|
| `/chat_ws` | `profiles.consumers.ExtendedChatConsumer` | `str(user_id)` персональная | Мессенджер, уведомления |
| `/ws/post/<id>/comments/` | `comments.consumers.PostCommentsConsumer` | `post_comments_<id>` | Живые комментарии на странице поста |
| `/ws/feed/` | `posts.consumers.FeedConsumer` | `feed` общая на всех | Живая лента: лайки, счётчики, новые/удалённые посты |

## Приложения — что где

### `profiles` — самое большое приложение, ядро проекта

Модель пользователя (`AUTH_USER_MODEL = 'profiles.User'`), мессенджер, личные задачи,
заметки, календарь, уведомления, статус сотрудника.

- **`models.py`** — `User` (расширяет `AbstractUser`: аватар, обложка, должность,
  телефоны, `employee_status`), `MessageReaction`/`MessageReply` (расширения над
  сторонней библиотекой чата, см. ниже), `Task`, `Note`, `Event`, `Notification`.
- **`views/`** — **пакет**, не файл (был разбит из монолитного `views.py` на ~1000
  строк). Модули по доменам:
  - `_common.py` — общие хелперы: `clear_user_cache`, `push_chat_event`
    (централизованная отправка Channels-события в группу пользователя), `notify`
    (создать `Notification` + запушить её через тот же канал).
  - `profile.py` — `AddProfile`/`SettingProfile` (**оба всегда редактируют
    `request.user`**, `user_id` в URL — вымерший исторический параметр, см. ниже),
    `ShowUsers`, `ShowPhones`, `EmployeeStatusUpdateView`.
  - `chat.py` — весь мессенджер (см. отдельный раздел ниже).
  - `tasks.py`, `notes.py`, `calendar.py`, `notifications.py` — CRUD-вьюхи
    соответствующих виджетов на странице профиля, все AJAX/JSON.
  - `__init__.py` — реэкспортирует все имена через `__all__`, чтобы
    `from .views import *` в `urls.py` и `from .views import clear_user_cache`
    в `signals.py` продолжали работать без изменений.
- **`consumers.py`** — `ExtendedChatConsumer(ChatConsumer)`, расширяет чат-consumer
  стороннего пакета `django_private_chat2` собственными типами событий
  (редактирование/удаление сообщений, реакции, ответы, уведомления). **Не
  переопределяйте методы с именами, совпадающими с методами базового класса** —
  см. предупреждение ниже.
- **`context_processors.py`** — данные, доступные во всех шаблонах: дни рождения
  сегодня/завтра, содержимое колокольчика уведомлений, список онлайн-коллег,
  счётчик непрочитанных сообщений.
- **`middleware.py`** — `UserActivityMiddleware`, обновляет `last_activity` на
  каждый запрос (используется для расчёта "онлайн"/"был недавно").
- **`signals.py`** — `pre_save`-сигнал на `MessageModel` санитизирует HTML в тексте
  сообщения через `nh3.clean` (whitelist тегов `b/i/u/s`) — единственная защита от
  XSS в чате, полагается на нативное экранирование Django-шаблонов как второй рубеж.

#### Мессенджер (`profiles/views/chat.py`, `consumers.py`, `templates/profiles/messages.html`)

Построен поверх стороннего пакета `django_private_chat2`
(`MessageModel`, `DialogsModel`, `ChatConsumer`, WebSocket-протокол с числовыми
`msg_type`). Проект **не форкает** эту библиотеку, а расширяет её:

- `MessageReaction`, `MessageReply` — отдельные модели-расширения с FK на
  `django_private_chat2.MessageModel`, а не патч самой модели (чтобы не
  форкать чужие миграции).
- Кастомные `msg_type`, добавленные проектом поверх протокола библиотеки:
  `100` — сообщение отредактировано, `101` — удалено, `102` — реакция,
  `103` — уведомление (из общей системы уведомлений `profiles.models.Notification`),
  `104` — новое сообщение-ответ (reply), `105` — обновилась цитата в ответе
  (когда отредактировали оригинал, на который кто-то отвечал).
- **Отправка обычных сообщений** идёт через нативный WebSocket-протокол
  библиотеки. **Ответы (reply)** идут через отдельный HTTP-эндпоинт
  (`SendMessageWithReplyView`, `POST /send-message-reply/<user_id>/`), потому что
  библиотека не поддерживает `reply_to` в своём протоколе, а её встроенный
  валидатор входящих WebSocket-сообщений отклонил бы незнакомое поле.

**⚠️ Важное предостережение** (стоившее реальной регрессии в этом проекте): при
отправке HTTP-инициированного события в WebSocket-группу пользователя
(`channel_layer.group_send(str(user_id), {'type': 'some_name', ...})`) **имя
`type` не должно совпадать с именем метода, уже определённого в базовом классе
`ChatConsumer`** библиотеки — например, `new_text_message` уже занят библиотекой
для доставки обычных сообщений. Если переопределить метод с таким же именем в
`ExtendedChatConsumer`, это **полностью перекрывает** библиотечный обработчик:
обычные сообщения перестают доходить онлайн-получателю (падают с `KeyError`,
потому что кастомный обработчик ждёт других полей). Правило: для кастомных
событий всегда используйте уникальное имя, не пересекающееся с методами
`django_private_chat2.ChatConsumer` (сейчас используется `new_reply_message`
вместо `new_text_message`).

Ленивая подгрузка старых сообщений (`LoadMoreMessagesView`) использует курсор
по `id` (`before_id`), а не числовой offset — offset "плыл" бы при появлении
новых сообщений в диалоге во время скролла.

### `posts` — лента ("Новости") и "Моя страница"

- **`models.py`** — `Post` (поле `photo` помечено как устаревшее, **не удалять
  без миграции данных** — на момент написания у нескольких постов есть значения
  в этом поле, актуальный способ прикрепить изображения — `PostImage`),
  `PostImage`, `PostFile`.
- **`views.py`**:
  - `PortalHome` — лента ("Новости"), `LoginRequiredMixin`.
  - `AddPost` — "Моя страница" (`/profile/<username>/`) — и просмотр чужого
    профиля, и форма создания поста одновременно; `LoginRequiredMixin` требует
    входа для просмотра (`username` в URL может быть чужим — это нормально,
    так открывается профиль коллеги).
  - `ShowPost` — страница одного поста с комментариями; `GET` открыт всем
    (включая неавторизованных), `POST` (создание комментария) требует логина.
  - `SettingPost`, `PostDeleteView` — редактирование/удаление, `get_queryset()`
    жёстко фильтрует `author=request.user` (без этого — IDOR: любой залогиненный
    мог редактировать/удалять чужие посты, это было реальной уязвимостью).
  - `toggle_like`, `post_likers` — лайк поста и JSON-список лайкнувших (для
    модального окна, см. `base.html`).
  - `NewPostsFeedView` — `GET /posts/new-since/<last_post_id>/`, отдаёт HTML
    новых постов (рендерит тем же `includes/post_card.html`, что и обычная
    лента) для кнопки "Есть новые посты".
- **`consumers.py`** — `FeedConsumer`, WebSocket-канал живой ленты на
  `/ws/feed/`, одна общая группа `feed` (не привязана к конкретному посту, в
  отличие от `comments.PostCommentsConsumer` — в ленте одновременно видно
  много карточек, событие должно доходить всем, кто её смотрит).
- **`realtime.py`** — `broadcast_post_created`, `broadcast_post_like_toggled`,
  `broadcast_post_comment_count_changed`, `broadcast_post_deleted` — рассылка
  в группу `feed`. Импортируется и из `comments/realtime.py` (счётчик
  комментариев у карточки поста в ленте меняется, когда комментарий
  создан/удалён на странице самого поста).

#### Живая лента (реалтайм на странице "Новости")

- **Лайк/дизлайк** любым пользователем обновляет счётчик у карточки поста в
  реальном времени у всех, кто сейчас на ленте (или на "Моей странице" —
  используется тот же `includes/post.html`).
- **Новый/удалённый комментарий** обновляет счётчик комментариев у карточки.
- **Удаление поста** убирает карточку у всех открытых вкладок без reload.
- **Новый пост** НЕ добавляется в ленту автоматически — вместо этого
  показывается кнопка "Есть новые посты" (не сбивает читающего ленту
  пользователя), по клику подгружает и вставляет карточки сверху.
  **Кнопка рендерится только в `index.html`** (страница ленты), а не в
  переиспользуемом `includes/post.html` — тот же partial используется и на
  "Моей странице", где кнопка не нужна. WS-подписка на `post_created` в
  `includes/post.html` ищет кнопку по `id` и просто ничего не делает, если
  её нет на странице; остальные события (лайк/комментарий/удаление) работают
  везде одинаково через один и тот же `connectFeedSocket()`.
- Карточка поста вынесена в переиспользуемый `templates/includes/post_card.html`
  (тот же приём, что и с комментариями) — HTML рендерится один раз на сервере,
  не дублируется в JS. `includes/post.html` — обёртка со списком, модалкой
  удаления и всей JS-логикой; `includes/post_list_fragment.html` — просто
  цикл `{% for post in posts %}{% include "post_card.html" %}{% endfor %}`,
  переиспользуется и при обычном рендере, и в ответе `NewPostsFeedView`.
- Обработчики лайка и удаления поста — через event-делегирование
  (`$(document).on('click', '.like-button', ...)` в `base.html`, а не
  `$('.like-button').click(...)`) — иначе не работали бы для карточек,
  добавленных динамически кнопкой "Есть новые посты".

#### Формы создания поста/комментария — пилюля в стиле мессенджера

И `templates/profiles/profiles.html` (форма поста), и `templates/post/single.html`
(форма комментария) используют один и тот же визуальный паттерн, что и форма
отправки в мессенджере (`templates/profiles/messages.html`): аватар слева,
овальная пилюля (`rounded-3xl`) с textarea внутри, кнопка эмодзи внутри
пилюли справа, круглая кнопка отправки/публикации **тоже внутри пилюли**
(последний элемент flex-ряда, не отдельно снаружи). У формы поста дополнительно
есть скрепка слева внутри пилюли — Alpine-дропдаун с выбором "Фото"/"Файл"
(`attachOpen` в `x-data`), у комментария скрепки нет (в модели `Comment` нет
полей для вложений). Preview выбранных файлов (миниатюры с крестиком удаления)
показывается отдельным блоком **над** пилюлей и появляется только при выборе
файлов — существующий JS-механизм (`activateImagePreview`) не менялся,
только переехала разметка.

### `comments` — комментарии к постам

Изначально было почти пустым приложением (вся логика жила в `posts.ShowPost`).
Сейчас полноценный домен:

- **`models.py`** — `Comment`. Свойство `is_edited` вычисляется сравнением
  `comment_updated` (`auto_now=True`) и `comment_pubdate` (`auto_now_add=True`) —
  если разошлись больше чем на секунду, комментарий редактировали. Отдельного
  поля-флага нет осознанно, чтобы не плодить лишнее состояние.
- **`views.py`** — `CommentEditView`/`CommentDeleteView` (только автору,
  `comment_author=request.user`), `CommentToggleLikeView`, `CommentLikersView`.
- **`consumers.py`** — `PostCommentsConsumer`, отдельный лёгкий WebSocket-consumer
  для живых обновлений комментариев на странице поста (создание, редактирование,
  удаление, лайк). **Намеренно не переиспользует** `ExtendedChatConsumer` из
  `profiles` — своя группа на пост (`post_comments_<id>`), а не на пользователя,
  и осознанное решение не рисковать повторением бага с конфликтом имени
  обработчика (см. предупреждение в разделе `profiles`).
- **`realtime.py`** — общий модуль для рассылки WS-событий и уведомления автора
  поста о новом комментарии (`Notification.Kind.POST_COMMENTED`); используется и
  из `comments/views.py`, и из `posts/views.py` (создание комментария — там же,
  в `ShowPost.form_valid`), без циклических импортов между приложениями.

**Ключевое архитектурное решение по правам в живых комментариях:** HTML одного
комментария рендерится **один раз на сервере** (`templates/includes/comment.html`)
и рассылается как есть всем, кто сейчас смотрит страницу поста. Кнопки
"Изменить"/"Удалить" **всегда присутствуют в разметке**, но скрыты CSS-классом
`comment-owner-only` — JS на клиенте показывает их, только если
`data-author-id` элемента совпадает с текущим `currentUserId`. Так рендер
идентичен и при обычной загрузке страницы, и при вставке через WebSocket, где
сервер физически не может знать персонально, кто из подписчиков сейчас смотрит.
Тот же приём — для состояния лайка (`data-liked-user-ids`).

### `category`, `gallery`, `login`, `register`, `phonebook`, `sitesettings`

Более простые вспомогательные приложения:

- **`category`** — модель `Category`, отдельные `ListView` для фильтрации постов,
  пользователей и телефонов по категории.
- **`gallery`** — независимая общая фотогалерея (`AddImages`, требует логина).
- **`login`/`register`** — стандартный auth-flow плюс сброс пароля через
  "контрольное слово" (`security_answer` на модели `User`, не email — сеть
  изолирована, email может быть недоступен).
- **`phonebook`** — простой справочник телефонов, `PhoneBook(UpdateView, DetailView)`.
- **`sitesettings`** — синглтон-модель `SiteSettings` (название сайта, логотип),
  доступна во всех шаблонах через `context_processors.site_settings`.

## Ключевые архитектурные паттерны проекта

### Layout: `{% block content_layout %}` и хлебные крошки

`templates/base.html` определяет общий каркас: `{% block Profiles %}` (боковая
колонка профиля, обычно пустая) + `.flex.min-w-0.flex-1.flex-col.gap-4{% block content_layout %}`
(объединяет `{% block sidebar_wrapper %}` и `{% block content %}` в одном
flex-контейнере, `md:flex-row` по умолчанию). Если странице нужна
ограниченная по ширине и центрированная колонка (сейчас так на "Новостях"),
ширину задают именно через `content_layout`, а не изнутри `content` —
например `index.html`: `{% block content_layout %} md:flex-row-reverse
md:w-2/3 md:flex-none md:mx-auto{% endblock %}`. `md:flex-none` обязателен
рядом с `md:w-2/3` — без него `flex-1`, заданный в `base.html` на этом же
элементе, растянет контейнер обратно на всю ширину поверх заданных 2/3.

**Не задавайте ограничение ширины внутри переиспользуемых partial'ов**
(`includes/post.html` и т.п.) — на "Моей странице" тот же partial соседствует
с панелью задач/заметок в отдельной колонке, и фиксированная ширина внутри
partial'а сжимает его вне зависимости от родительского layout'а (была реальная
регрессия: `md:w-2/3` на ленте применился ко всем случаям использования
`includes/post.html`, из-за чего на "Моей странице" сжались и заглушки).

Хлебные крошки (`base.html`, блок `{% block breadcrumb %}`) по умолчанию
показывают "Новости" — если для новой страницы нужен другой путь, обязательно
переопределяйте блок в дочернем шаблоне; раньше это игнорировалось, и на всех
страницах виднелась одна и та же крошка.

### Пакет `views/` вместо монолитного `views.py`

`profiles/views.py` разросся до ~1070 строк, смешивая профиль/чат/задачи/
заметки/календарь/уведомления. Разбит на пакет `profiles/views/` по доменам
(см. выше). Это низкорисковый механический рефакторинг: `urls.py` использует
`from .views import *`, и пакетный `__init__.py` с явным `__all__` сохраняет это
рабочим без изменений в других файлах. Если `posts/views.py` или другой файл
вырастет до сравнимого размера — стоит применить тот же приём.

### `push_chat_event` / `notify` — единая точка WebSocket-рассылки

`profiles/views/_common.py` содержит `push_chat_event(user_id, event_type,
**payload)` — тонкая обёртка над `channel_layer.group_send`, устраняющая
повторяющийся паттерн `channel_layer = get_channel_layer(); async_to_sync(...)`,
который раньше повторялся в 6+ местах. `notify(...)` поверх неё создаёт запись
`Notification` и одновременно пушит её через тот же канал. При добавлении нового
типа realtime-события — используйте эти хелперы, а не пишите
`get_channel_layer()` заново.

### `get_or_create`/`update_or_create` для toggle-операций

Реакции на сообщения, лайки постов/комментариев — везде, где есть паттерн
"поставить/снять" от двойного клика, используется атомарный
`update_or_create`/`filter().exists()`, а не `filter().first()` +
`create()`/`save()` по отдельности — второе даёт гонку при быстром двойном клике
(`IntegrityError` на `unique_together`).

### Проверка владения через `get_queryset()`, не в `post()`/`get()`

Для `UpdateView`/`DeleteView` право редактирования/удаления проверяется
переопределением `get_queryset()` (например,
`Post.objects.filter(author=self.request.user)`), а не проверкой внутри метода.
Если объект не найден в отфильтрованном queryset — Django сам вернёт 404.
Стандартный Django-паттерн, применяется последовательно во всём проекте после
серии находок аудита (`AddProfile`/`SettingProfile`, `PostDeleteView`,
`SettingPost` изначально были без такой фильтрации — классический IDOR).

### Живые обновления без переиспользования чужого WebSocket-протокола

Когда нужен WebSocket для новой фичи (живые комментарии, живая лента) —
заведён **отдельный лёгкий consumer** на отдельном URL, а не встраивание в
существующий чат-канал. Урок из бага с `new_text_message` (см. раздел
`profiles`): чужой протокол легко случайно сломать, переопределив метод с
совпадающим именем. Для независимых фич — свой consumer, своя группа Channels.

`comments/realtime.py` и `posts/realtime.py` импортируют друг друга (создание
комментария меняет счётчик у карточки поста в ленте, и наоборот не требуется)
— оба импорта **ленивые, внутри функций**, а не на уровне модуля, специально
чтобы не создавать циклическую зависимость между `comments` и `posts` при
загрузке Django-приложений.

## Тестирование изменений

В проекте нет автотестов для большинства пользовательской логики (`tests.py` в
каждом app в основном пустые заглушки). Проверка вживую делается так:

```python
# Через Django test client — быстрый способ проверить права/статусы без браузера
from django.test import Client
from django.contrib.auth import get_user_model
User = get_user_model()
c = Client()
c.force_login(User.objects.first())
r = c.post('/some-url/', {'field': 'value'}, HTTP_HOST='127.0.0.1')
print(r.status_code, r.json())
```

`HTTP_HOST='127.0.0.1'` обязателен — `ALLOWED_HOSTS` в `settings.py` этого
требует. Всегда: `manage.py check` перед перезапуском сервера, живой AJAX-запрос
через test client на изменённый эндпоинт, ручная проверка в браузере для
JS/WebSocket-функциональности (test client не умеет в WebSocket).

**После изменений в WebSocket-consumer'ах или моделях — обязательно
перезапускать Daphne**, `runserver` их не подхватывает и не поддерживает ASGI.

## Frontend: без сборки, без npm

Все JS/CSS-библиотеки лежат в `static/` как обычные файлы, подключаются через
`{% static %}` в шаблонах. Tailwind — не собранный CSS, а browser-JIT компилятор
(`static/js/tailwinds.js`), сканирующий классы прямо в разметке во время
загрузки страницы — из-за этого в проекте нет `npm run build`/webpack-конфига,
классы Tailwind можно писать прямо в HTML и они сработают сразу.

Alpine.js используется для мелкой интерактивности (дропдауны, модалки без
полноценного JS-компонента). jQuery — для унаследованного кода (маски телефонов,
частично лайки постов). Feather Icons — иконки, рендерятся через
`data-feather="name"` + `feather.replace()` в JS.

## Известные технические долги (не критично, но стоит знать)

- `Post.photo` — устаревшее поле, у части существующих постов есть в нём данные;
  правильный путь прикрепления изображений — `PostImage`, но поле нельзя удалить
  без миграции данных.
- `social_network/routing.py` — параллельная, менее актуальная копия
  WebSocket-роутинга из `asgi.py`; держится синхронной вручную, реального
  дублирования логики стоит избегать при следующей ревизии.
- В `apps/comments` нет отдельных тестов на IDOR для новых вьюх
  (`CommentEditView`/`CommentDeleteView`/`CommentLikersView`) — проверено вручную
  через test client при разработке, но не закреплено автотестом.
